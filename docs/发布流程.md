# 发布流程

## 0. 命令

```bash
node scripts/release.ts           # 打包 + 全部校验（不推送）
node scripts/release.ts --push    # 补 tag + 提交 + 推送 + 线上验证
node scripts/release.ts --tags-only  # 只补缺少的 tag 并推送（不提交、不动分支）
node scripts/release.ts --check   # 只校验，不打包不写盘（CI 用）
node scripts/release.ts --verify  # 只验线上：每个版本都按 tag 取得到且哈希一致

node scripts/build.ts             # 只打包 + 生成索引
node scripts/build.ts --check     # 只校验索引与产物
npm run typecheck                 # 类型检查，只覆盖 src/ 与 types/ 下的 .ts / .tsx
```

**日常发布只需要 `node scripts/release.ts --push` 一条命令。** 它把下面第 1～7 节
的全部步骤串起来，并且补上了此前**唯一没有任何校验的一环** —— 见第 6 节。

**只补 tag 时用 `--tags-only`。** 它不提交、不动分支，只推 `refs/tags`。
修「索引里引用的版本取不到」（第 1.2 节那次 404）只需要它 —— 包早就提交在 main 上了，
改分支指针与修这个问题毫无关系。

改版本之外的所有步骤 —— 打包、算哈希、更新索引 —— 都由脚本完成。**打包脚本本身零依赖**，
只需要 Node 23.6 以上（`.ts` 由 Node 直接执行，不经过编译），手写单文件插件走这条路就够了。
从 `src/` 构建的那条快车道另需三个 devDependency：`esbuild` 负责打包，`typescript` 与
`@types/react` 负责类型检查。详见 [src/README.md](../src/README.md)。

## 1. 顺序

```
改版本 → node scripts/release.ts --push
```

展开来是：

```
改版本 → 打包 → 重新签名 → 实际安装一次 → 补 tag → 提交 → 推送 tag → 推送分支 → 线上验证
```

脚本把「打包」与「算哈希」合成了一步，因此这两者不可能再颠倒。索引里的哈希必然对应刚打
出来的包 —— 这条曾经是最容易出错的地方（改了源码忘了重新打包），现在由结构本身排除。

「重新签名」**不能**由脚本完成（需要私钥），因此它仍是链路上唯一需要人记住的动作。
`--check` 会专门拦它 —— 见 3.1。

> **`release.ts` 不会替你签名。** 它的顺序是「先 `build`（会提醒签名）→ 你签名 →
> `--check`（会拦没签名的索引）→ `--push`」。签名这一步没有捷径：私钥不在脚本够得着的地方。

### 1.1 一次真实事故：索引推上去了，tag 没推 —— 所有人的市场都装不了插件

2026-10-04，用户报「市场里装任何插件都弹 404」：

```
cdn.jsdelivr.net：下载失败: HTTP 404 Not Found
  （https://cdn.jsdelivr.net/gh/Rinntheor/modulith-plugins@notes-v1.0.3/dist/com.modulith.sample.notes-1.0.3.lcp）
raw.githubusercontent.com：网络错误 … dns error (os error 11004)
```

根因不是网络、不是 CDN 缓存、也不是包坏了：**索引里 10 个插件的「最新版本」全都没有
对应的 git tag**。宿主是用索引里的 `version.tag` 拼下载地址的
（应用仓库 `src/config/pluginRegistry.ts`），远端没有那个 ref，jsDelivr 只能 404。

时间线是清楚的：最后一个 tag `kanban-v1.0.2` 打于 2026-09-20，此后 09-24 至 09-27
一直在升版本、重打包、重签索引、推 main，**一次 `git tag` 都没执行**。

而工具层**一点都没拦住**：`build.ts` 从清单版本推出 tag 字符串
（`tag: \`${dirName}-v${version}\``），从头到尾不读 git；它的校验只问「dist 里那个
文件在不在、哈希对不对」。`--check` 同样不查 tag。于是「索引先行、tag 未打」能一路
绿灯通过全部检查，只剩文档里的 tag 纪律在撑 —— 而纪律正是这次没被执行的东西。

**修法有两层，两层都已落地：**

1. **补上缺失的 tag（救回线上）**：那些 `.lcp` 早已提交在 main 上，缺的只是 ref。
   `node scripts/release.ts --tags-only` 会为每个缺 tag 的索引版本找到「含有该包、且清单
   版本正好等于它」的最新提交并打上 tag，然后**只推 tag**（不提交、不动分支），
   最后验证线上可取。若要连索引一起发，用 `--push`。
2. **让这类状态在工具层不可能通过（防复发）**：`release.ts` 把「索引只能引用远端
   真的取得到的版本」变成一条硬判据。`--check` 现在会把缺 tag 当作**失败**，
   CI 与推送前都能拦住。

## 2. 改版本

编辑 `plugins/<名称>/manifest.json` 的 `version`。

版本位的选择见[贡献指南](../CONTRIBUTING.md)第 5 节。**新增权限属于 MAJOR** —— 权限变化
会触发用户侧的确认流程，当成小版本会让升级在用户那里显得突然。

## 3. 打包并生成索引

```bash
node scripts/build.ts
```

输出形如（**本仓库当前是 11 个插件、31 个版本**；下面是给 `hello` 与 `kanban` 各加一个
新版本时的样子）：

```
  ✔ dist/hello/1.0.4.lcp  8170 字节  d1d3ad1e016e…
  ✔ dist/kanban/1.0.6.lcp  105600 字节  …
索引已写入 index.json：11 个插件、33 个版本，哈希全部复核通过。
```

（路径的**形状**是真实的，字节数是示意 —— 下一次发布时它们会不一样。）

产物路径是 **`dist/<插件目录名>/<版本号>.lcp`**。已经发布过的版本号不走这条规则：
脚本读索引里记录的 `package.path` 并**原样沿用**，因此历史版本继续留在
`dist/<插件 ID>-<版本号>.lcp` 那个平铺位置上。这不是兼容层的权宜之计，而是必须的：

- 索引里的 `package.path` 是客户端**直接拼接**的下载地址（宿主 `pluginMarket.ts` 的
  `registrySources(version.tag, version.package.path, …)`），客户端不解析它的结构；
- `release.ts --check` 会验证「tag 指向的提交里含有 `package.path` 那个包」，而旧 tag 的
  提交树里文件就在旧的平铺路径上。

两个理由指向同一件事：**已经发布过的版本，路径从此不可变**，否则老用户会在安装时拿到
404。新布局只能作用于将来发布的版本。`build.ts --check` 对两种形状一视同仁 —— 它以索引
里的 `package.path` 为唯一准绳，逐个文件核对存在性与哈希，不解析目录结构。

脚本做四件事，任何一步失败都不会写出产物：

1. **校验全部清单。** 问题一次性列全，而不是「改一个跑一次」。校验只检查**写法**是否
   可能合法，权限名是否真实存在由宿主的权限注册表决定 —— 本仓库不再维护第二份权限名单。
2. **打包为 `.lcp`。** 压缩的是插件目录的内容，因此 `manifest.json` 位于包根部。
3. **并入索引。** 保留历史版本条目。索引必须并入而不是重建：工作区里只有当前版本的源码，
   直接重建会让旧版本连同它的哈希一起消失。工作区里已经不存在的插件目录会被整体移出
   索引，并打印一条警告。
4. **复核。** 索引引用的每个包都必须存在，且哈希与记录一致。这一步能抓住「手工改过
   `index.json`」与「`dist/` 里的包被删或被换」两类问题。

新增插件不需要手工改索引 —— 脚本扫描 `plugins/` 自行发现。

## 3.1 重新签名（改了索引就必须做）

**索引是有签名的，而且客户端会验签。** 因此索引一变，签名就必须跟着变 —— 忘了这一步的
后果不是「新插件看不到」，而是**所有人的市场都打不开**。

```powershell
# 在应用仓库里执行（tauri CLI 在那里）
cd ..\modulith-desktop

# ① 先清掉 TAURI_SIGNING_PRIVATE_KEY。
#
#    这不是可选的：同一个终端里刚跑过 pnpm release / pnpm tauri build 时，它一定还留着
#    （构建链路需要它，值是私钥**路径**），而 signer sign 见到它就会把 -f 当成冲突参数：
#
#      error: the argument '--private-key-path <PRIVATE_KEY_PATH>'
#             cannot be used with '--private-key <PRIVATE_KEY>'
#
#    两者为什么对同一个变量有不同要求，见应用仓库「版本管理」第 7.2.3 节的实测表格。
Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY -ErrorAction SilentlyContinue

# ② -f 不能省：signer 必须知道用哪把私钥。
#    也可以改用 TAURI_SIGNING_PRIVATE_KEY_PATH 环境变量，并复用同一个终端会话。
#    口令来自 TAURI_SIGNING_PRIVATE_KEY_PASSWORD，没设时它会交互式询问。
pnpm tauri signer sign -f "$env:USERPROFILE\.tauri\modulith.key" "..\modulith-plugins\index.json"

# ③ 签完立刻复核：索引比签名新、哈希不符这类问题都会被拦下来
cd ..\modulith-plugins
node scripts/build.ts --check
```

tauri 会把签名写在同名的 `index.json.sig` 里。**把这个文件与 `index.json` 一起提交。**

三点说明：

- **`build.ts` 不会替你签名**，它刻意不接触私钥（它只负责打包与索引）。但它会在写完后
  打印上面这条命令，并且 `--check` 会把「索引改了但没重新签名」当作**错误**拦下来。
- **签名与索引必须同一次提交。** 分开提交意味着中间那一瞬间远端是坏的 —— 而 CDN 不会
  替你等待。
- **签名用的密钥与应用更新是同一把。** 公钥随应用发布（写在应用仓库的
  `src-tauri/tauri.conf.json` 里），因此客户端不需要额外配置。密钥的处置见应用仓库的
  [版本管理](../../modulith-desktop/docs/02-开发指南/版本管理.md)第 7 节。
- **本仓库不做密码学验签，但会检查签名的字节形状。** `--check` 里有**两道**与签名有关的
  检查，都不需要私钥：

  | 检查 | 拦住什么 |
  | --- | --- |
  | 修改时间比较（`index.json` 比 `.sig` 新就报错） | 「改了索引忘了签名」 |
  | `signatureShapeProblem()`：整个文件必须是合法 base64、长度是 4 的倍数、`=` 只在末尾、解出 4 行 minisign、数据段 74 字节 | 「**签名文件本身坏了**」← 见 3.2 |

  两道都**不能证明签名有效**（签错文件、用错私钥仍发现不了）。真正的验签在客户端
  （`verify_plugin_index`），它一旦失败就是**所有人的市场都打不开**。因此推送前请用**公钥**
  实跑一次验签（`minisign -V` 或 `tauri signer verify`；验签不需要私钥，所以这一步也能放进 CI）。

### 3.2 一次真实事故：签名文件尾部多了 30 个字节，市场对所有人打不开

2026-10-07，用户报：

```
无法获取插件列表
无法获取插件索引。
raw.githubusercontent.com：包非法: 签名不是合法的 base64：Invalid symbol 61, offset 394.
cdn.jsdelivr.net：包非法: 签名不是合法的 base64：Invalid symbol 61, offset 394.
```

`index.json.sig` 的前 396 字节是**正确且新鲜**的签名，但它后面被多写了 30 个字节 ——
也就是紧接着要跑的那条命令：

```
node scripts/build.ts --check
```

`61` 就是 `=`。客户端的解码是严格的：整个文件必须是合法 base64，多出来的字节让 `=`
不再位于末尾，解码在 offset 394 失败，于是客户端拒绝使用**整份索引**。两条候选来源
拿到的是同一份坏文件，因此两条一起失败 —— 而"已安装的插件不受影响"这个提示会让人以为
问题不大。

**修法是把文件截回 396 字节，不需要私钥**：坏掉的只是多余字节，签名本身没变。

**为什么此前一点都拦不住：**

- 那道修改时间比较是**通过**的 —— 签名确实被改过、而且比索引新；
- `release.ts --check` 只查 tag；
- 没有任何一处看签名的字节。

还有一个**特别容易骗过验证**的性质：`Buffer.from(str, 'base64')` 与多数宽松解码器会
**静默跳过**非法字符，于是"解一下再验签"会得出「签名有效」这个错误结论。第一版线上
验证脚本就是这么被骗过去的。**只有显式的字符表与补位检查能发现它** —— 这就是
`signatureShapeProblem()` 存在的理由，它正是照着这条事故的形状写的。

推送前建议跑一次线上验证（两条来源 + 与客户端一致的 `?t=` 查询串）：
见 `staging/verify-online-index.cjs`。

**顺带记下 jsDelivr 的行为**：仓库修好之后，`@main` 的裸地址与 `?t=` 地址在一段时间内
仍然返回**旧的**坏副本，连续两次 purge（`https://purge.jsdelivr.net/gh/<owner>/<repo>@main/<file>`）
之后才变成新内容。而客户端是"两条来源都失败才算打不开"（`pluginMarket.ts` 的 `fetchIndex`），
因此只要 GitHub 直连那条已经修好，市场就能打开 —— 这一点决定了抢修时先看哪一条。

## 4. 为什么包是确定性的

条目按名称排序，时间戳固定为 1980-01-01，压缩级别固定，压不小就退回不压缩。因此
**同一份源码重复构建得到同一串字节**。

这不是洁癖。索引里记录的 `sha256` 只有在输出确定时才有意义 —— 否则它只能证明「这个包没被
改动过」，不能证明「这个包就是这份源码构建出来的」。

**前提是同一个 Node / zlib 版本。** deflate 的输出由 zlib 实现决定，而脚本的二次打包
比对是**同一进程内**的比较，挡不住版本差异。由于 `--check` 会把「当前源码打包出的哈希
≠ 索引记录」当作错误，换 Node 版本后跑校验可能得到一次**假失败** —— 先确认 Node 版本，
再判断是不是真的改了源码。

**从 `src/` 构建的插件还有一个前提：仓库根的 `tsconfig.json` 要原样在场。** esbuild 会自己
去读它，读到与否会改变产物里有没有那一行严格模式指令，因此产物的字节不只取决于 `src/`
下的代码。这是构建链路的一个真实缺陷，已知问题与修法记在
[src/README.md](../src/README.md)。

**"改了源码忘了升版本"现在会被拒绝。** `build.ts` 在落盘之前检查：若某个版本号已在索引里
存在、而当前源码打包出的哈希不同，直接失败并要求升一个版本。此前这种情况会正常通过，于是
同一个版本号可能出现两份内容 —— 而 README 承诺的「同一个版本号下的内容永远一致」也就只剩
tag 纪律在撑。

脚本每次打包都会**连打两次并比对字节**，因此一旦有人引入时间戳、随机顺序之类的非确定
因素，构建会当场失败，而不是安静地生成一个每次都不一样的包。

## 5. 实际安装一次

不要只看「打包成功」。装一次：

```
设置 > 插件 > 安装插件 > 从插件包安装
```

确认三件事：侧边栏出现模块、模块能操作、**关掉应用重开后状态还在**。第三件事只有真正的
持久化路径能通过，而它恰好最容易被「我以为写了」掩盖。

## 6. 打 tag

**自动化了 —— 但仍然要理解它在做什么。** `release.ts --push` 会自动补上缺失的 tag，
你不用再手打 `git tag`。下面是它替你做的事，以及为什么这件事**不能**省掉。

每个插件的每个版本一个 tag：

```bash
git tag -a hello-v1.0.0 -m "hello 1.0.0" 947c9f3f   # 由 release.ts 自动完成
```

### 6.1 为什么非要有 tag（为什么不能改成走分支）

技术上**不是**必须的：`pluginRegistry.ts` 的 `ref` 可以是分支名，实测
`@main` 能取到同一份文件。但分支引用意味着**内容可变**，而索引里记着 `sha256`：

- 一旦有人在同一分支上改了那个文件，所有客户端都会拿到"哈希不符"并**拒绝安装** ——
  而那个错误看起来像"发布者的包坏了"，排查方向从一开始就是错的；
- jsDelivr 对分支引用的缓存是若干小时，对 tag 引用则是**永久** ——
  于是每次发版都要额外去清 CDN，而清了也未必立刻生效（见 9.1）。

tag 是让「**版本号 = 一份确定的内容**」这句话真正成立的机制，也是永久缓存的前提。
所以正确的做法不是把 tag 去掉，而是**让它自动产生、并在推送之前强制校验** ——
这正是 `release.ts` 做的事：补 tag → 推 tag → **确认线上可取** → 才推索引。
索引于是不可能领先于 tag，那次事故的形态在工具层被排除。

### 6.2 已发布的 tag 永不移动、永不删除

CDN 用 tag 作为缓存键，移动 tag 会让新老用户在同一个版本号下拿到不同内容 ——
这违反「版本号标识一份确定的内容」这条最基本的约定。改错了就发一个新版本，
不要回头改历史。`release.ts` 只**新增** tag：已存在的 tag 它一律不碰
（存在即跳过），因此它不会在无意间把某个 tag 挪到新提交上。

### 6.3 它把 tag 指向哪个提交

指向「**含有那个 `.lcp`、且该插件的清单版本正好等于这个版本号**」的最新提交。

两个条件都必要：只看文件会选中「包在、而清单已经升到下一版」的提交；只看清单会选中
「清单对、包还没打出来」的提交。**它绝不兜底成"就指 HEAD"** —— 一个指向错误提交的 tag
比没有 tag 更糟，因为它会以一个看起来正常的状态被推出去。
找不到合适提交时它直接失败并让你人工确认，而不是猜一个。

（本次事故里 10 个 tag 全都合法地指向了 HEAD：HEAD 恰好就是最早满足那两个条件的提交。）

## 7. 提交与推送

`index.json` 与整个 `dist/`（含 `dist/<插件目录名>/` 那些新目录）都要提交 —— 它们**不在**
`.gitignore` 里，这是刻意的，理由见
仓库根 `README.md` 的「为什么同时提交源码与 .lcp」。

`node scripts/release.ts --push` 替你做的就是这个，**顺序是刻意的**：

```bash
git add -A
git commit -m "chore(release): 更新插件索引与产物"
git push origin --tags      # ← 先推 tag
git push origin HEAD        # ← 再推分支（索引在这一步才可见）
```

**为什么先推 tag。** 索引一被推上去就可能立刻有人去装（`?t=` 会让它尽快可见），
而那一刻 CDN 必须在那个 ref 上已经拿得到包。反过来的话，会出现一个「索引说有这么个
版本、而它的地址 404」的窗口 —— 那正是这次事故用户看到的错误。tag 先到，
这个窗口就不存在。

手工执行时也请保持这个顺序：**tag 先，分支后**。

### 7.1 推送被拒：`cannot lock ref 'refs/heads/main'`

这一条**真的会遇到**，而它看起来比实际严重得多。原文：

```
! [remote rejected] HEAD -> main
  (cannot lock ref 'refs/heads/main':
     is at c3f6269ac72dc57bded3d0ec250fcf75f96660b7
     but expected 947c9f3fcd2641446efef85c785b09d7ce46eb72)
```

**它说的是**：git 推送分支用的是**比较并交换** —— 推送前它记下"远端现在是 `947c9f3f`"，
写入时要求远端仍然是那个值，否则拒绝。这是防止覆盖别人工作的安全机制，不是数据损坏，
也不是你的本地坏了。

**常见原因**（按可能性排序）：

| 原因 | 特征 | 处理 |
| --- | --- | --- |
| 同一件事被执行了两次（另一个终端 / 另一台机器 / 脚本跑了两次） | 报错里的"远端值"**就是**你本地 HEAD 的提交号 | 什么都不用做 —— 远端已经是你要的那份内容 |
| 远端有本地没有的提交（别处推过东西） | 远端值不是你的 HEAD，且 `git fetch` 之后能看到新提交 | 先 `git fetch`，看清远端那些提交是什么，再决定合并或变基 |
| 有人强推过（历史被改写） | `git fetch` 之后本地与远端的共同祖先变了 | 少见，先弄清楚谁改的，**不要**跟着强推 |

**判断与恢复**：

```bash
git fetch origin
git rev-parse HEAD                    # 本地 HEAD
git log --oneline origin/main -5      # 远端 main

# 若两个提交号相同 → 已经一致，收工
# 若远端有本地没有的提交 → 先看清它们，再合并或变基，然后重新推
#   git rebase origin/main && git push origin HEAD:main
```

**永远不要用 `--force` 解决它。** 那条拒绝正是为了保护你还看不见的东西。

**卡在"tag 推上去了、分支没推"怎么办？** 这正是 `--tags-only` 存在的理由：
补 tag 与推分支是**两件独立的事**，前者写 `refs/tags`，后者写 `refs/heads/main`。
只修 404 就只需要前者。而 `release.ts` 在推送失败时会逐条报告**哪一步成了、
哪一步没成**，并给出可直接照抄的重试命令 —— 这条规则来自那次事故：
当时的脚本让异常冒到顶层，用户看到一屏 Node 栈，无法判断市场到底修好没有。

## 8. 什么时候跑 --check

```bash
node scripts/release.ts --check
```

它回答的问题是「索引与仓库内容是否还一致，以及**索引引用的版本在 git 里是否成立**」。
有用的时候：

- 拉取别人的改动之后，确认索引没有被漏掉重新生成。
- 推送之前（见下）。
- CI 里作为门禁。

它把两道检查叠在一起：

| 检查 | 由谁做 | 拦住什么 |
| --- | --- | --- |
| 索引 ↔ 产物（文件在不在、哈希对不对、签名配不配套、签名的字节形状合不合法） | `build.ts --check` | 改了源码没重打包、手工改过 `index.json`、改了索引忘了签名、**签名文件被追加了内容/改了编码**（见 3.2） |
| 索引 ↔ git（每个版本有没有 tag、tag 指向的提交里有没有那个包） | `release.ts` | **索引先行、tag 未打** ← 那次 404 事故 |

第二道是**新加的**，也正是此前缺失的那一环。缺 tag 会让 `--check` 以非零退出，
所以「推上去才发现装不了」这类事故现在在本地就会被拦住。

**它不只是校验索引与包，还会拦「索引改了但没重新签名」** —— 索引比签名新会返回非零（理由见 3.1）。所以它有两个常见用法，别混起来：

| 时机 | 结果 |
| --- | --- |
| 刚跑完 `build`、**索引确实变了** | 会在签名这一项报错，直到你重新签名 |
| 刚跑完 `build`、索引没变（重复运行） | 全部通过 |

因此它不是「跑完 build 就必然通过」，而是「把打包与签名两件事都核一遍」。刚改完插件就指望它通过，只会看到签名那一项失败 —— 那正是它想告诉你的事。

## 9. 推送之后

- **索引是唯一可变的那一份**，因此它是唯一需要绕缓存的。客户端请求它时带
  `?t=<时间戳>`。
- `.lcp` 走不可变 tag 地址，永久缓存，因此同一个 tag 下的内容永远不会变；README 同理。
- 应用侧的市场页会在下次拉取索引时看到新版本。

### 9.0 推送之后一定要验一次线上

```bash
node scripts/release.ts --verify
```

它逐个版本去 jsDelivr 按 **tag** 取包，比对字节与仓库里那份是否一致。
这是**唯一**能证明"用户点安装会成功"的检查 —— 本地校验只能证明仓库状态自洽，
证明不了 CDN 真的提供那份内容（那次 404 事故里，本地一切正常）。

`--push` 会在推送之后自动跑它，失败时给出下一步（清缓存 / 稍后重试）。

### 9.1 `?t=` 保证不了「立刻可见」← 本轮实际遇到过

早先这里写的是「索引走带查询串的地址，应当立刻可见」。**这个说法不成立**，本轮实际
撞上了：仓库里的 `index.json` 是正确的（当时的四个插件都在），而客户端市场里只列出了其中一个。

原因是 `?t=` 只解决「同一份远端内容的不同缓存键」——**如果 CDN 的回源副本本身还停在
旧提交上，换一个查询串也只会拿回同一份旧内容**。查询串让每次请求构成新的缓存键，
但缓存键背后取到的仍是那份没更新的副本。

因此：

```powershell
# 让 CDN 立刻刷新（需要 GitHub 授权；浏览器里打开更省事）
https://purge.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json
https://purge.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json.sig
```

不清也行 —— 分支引用的缓存是若干小时，之后自然会对。但**刚上架时作者和用户都会立刻
去看**，所以他们大概率看到旧索引，表现为「我推上去了，但市场里没有」。清一下省掉一轮
往返。

`.lcp` 与 `README.md` 按不可变 tag 取，**不需要清**。

### 9.2 客户端有两条候选来源

应用的取索引顺序是「jsDelivr → GitHub 直连」；用户配了「下载源」时反过来（GitHub 那条
排前面，并由后端把地址接在加速源域名之后）。因此**两条路都要能取到**，验证方式见
[审核与合并](审核与合并.md) 第 4.2 节。

## 10. 版本历史策略（为什么历史版本一直留着）

索引里每个插件保留着它的全部版本（当前 11 个插件、31 个版本），`dist/` 里也留着对应的
每一个包。**先说清楚一件事：它们在客户端目前没有任何消费方。**

### 10.1 客户端没有版本选择 UI —— 历史版本取不到、也用不上

宿主只有两个与"哪个版本"有关的地方，而两个都只看 `latest`：

| 位置 | 它做什么 | 依据 |
| --- | --- | --- |
| `latestVersionOf(plugin)` | 从 `versions[]` 里按 `plugin.latest` 找那一条 | 应用仓库 `src/services/pluginMarket.ts`。它是**安装与更新唯一的入口** |
| `planUpdate(plugin)` | 规划一次更新：比对已装版本与最新版本的权限、`runtime` | 同上，内部第一行就是 `const version = latestVersionOf(plugin)` |

市场界面里没有"选版本"这一项，`versions[]` 也没有任何`map` 到 UI 的地方。因此：

- 用户点"安装"永远装 `latest`；
- 已装插件点"更新"永远更新到 `latest`；
- **历史版本既不能被安装，也不能被回滚到** —— 当前没有回滚功能。

所以保留历史版本**不是**为了支持回滚。把这条说清楚很重要：否则会以为留着一堆没人用的
包是浪费，进而想去"清理"它。

### 10.2 那为什么还留着：它们是三件设计事实的副产物

1. **tag 不可移动（6.2）。** 版本号与内容的绑定靠 tag，而 tag 是 CDN 的永久缓存键。
   因此"删掉老包"并不会让老版本消失 —— 已发布的 tag 指向那个含有文件的旧提交，按 tag
   依旧能取到。删包真正能做到的是让 `main` 上的状态与索引不再自洽：`release.ts --check`
   明确要求**每个索引版本都存在于 `HEAD`**（`checkLocal` 的第一条），删了就过不了。
2. **jsDelivr 只能代理仓库内容，代理不了 GitHub Release 附件。** 产物必须在仓库里才有
   稳定的分发地址（见仓库根 `README.md`「为什么同时提交源码与 .lcp」）。把老版本挪到
   Release 附件，等于让那个 tag 地址 404 —— 客户端拼地址用的正是 `tag` + `package.path`。
3. **可审计性。** `git checkout <tag>` 能得到那份包，逐字节核对它与索引记录的 `sha256`、
   以及当时的源码是否一致。这是"某个版本到底发了什么"唯一的底本 —— 裁剪索引条目或产物
   之后，这段历史就只剩下一句无法验证的话。

三件事没有一件是"为了将来能回滚"。它们是**不可变 tag + CDN 只代理仓库 + 可审计**这三条
设计的直接后果，而这三条本身都还在生效。

### 10.3 因此

- **严禁删除已发布的 tag。** 它是版本号与内容之间的唯一绑定（6.2）。
- **默认不裁剪历史。** 裁剪索引条目或 `dist/` 里的老包，会失去上面第 3 条的审计底本；
  代价是仓库里多几个几十上百 KB 的文件。这个交换是划算的。
- 真到了必须下架某个插件的程度（例如恶意代码），正确的做法是**从索引里移除那个插件的
  全部条目并说明原因**，而不是删 tag 或删包 —— `build.ts` 在 `plugins/` 下找不到目录时
  会打印一条"该插件已从索引移除"的警告，那正是为这种情况准备的。
