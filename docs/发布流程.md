# 发布流程

## 0. 两条命令

```bash
node scripts/build.ts          # 打包 + 生成索引
node scripts/build.ts --check  # 只校验，不写任何文件
```

改版本之外的所有步骤 —— 打包、算哈希、更新索引 —— 都由脚本完成。脚本零依赖，只需要
Node 23.6 以上（`.ts` 由 Node 直接执行，不经过编译）。

## 1. 顺序

```
改版本 → node scripts/build.ts → 重新签名 → 实际安装一次 → 提交 → 打 tag → 推送
```

脚本把「打包」与「算哈希」合成了一步，因此这两者不可能再颠倒。索引里的哈希必然对应刚打
出来的包 —— 这条曾经是最容易出错的地方（改了源码忘了重新打包），现在由结构本身排除。

「重新签名」是后加的一步，因为它**不能**由脚本完成（需要私钥）。它现在是这条链路上唯一
需要人记住的动作，因此 `--check` 会专门拦它 —— 见 3.1。

## 2. 改版本

编辑 `plugins/<名称>/manifest.json` 的 `version`。

版本位的选择见[贡献指南](../CONTRIBUTING.md)第 5 节。**新增权限属于 MAJOR** —— 权限变化
会触发用户侧的确认流程，当成小版本会让升级在用户那里显得突然。

## 3. 打包并生成索引

```bash
node scripts/build.ts
```

输出形如（下面这一段是**单插件仓库**的样子，本仓库当前是 4 个插件、4 个版本）：

```
  ✔ dist/com.rinntheor.modulith.hello-1.0.0.lcp  6497 字节  d1d3ad1e016e…
索引已写入 index.json：1 个插件、1 个版本，哈希全部复核通过。
```

脚本做四件事，任何一步失败都不会写出产物：

1. **校验全部清单。** 问题一次性列全，而不是「改一个跑一次」。校验只检查**写法**是否
   可能合法，权限名是否真实存在由宿主的权限注册表决定 —— 本仓库不再维护第二份权限名单。
2. **打包为 `.lcp`。** 压缩的是插件目录的内容，因此 `manifest.json` 位于包根部。
3. **并入索引。** 保留历史版本条目。索引必须并入而不是重建：工作区里只有当前版本的源码，
   直接重建会让旧版本连同它的哈希一起消失。工作区里已经不存在的插件目录会被整体移出
   索引，并打印一条警告。
4. **复核。** 索引引用的每个包都必须存在，且哈希与记录一致。这一步能抓住「手工改过
   `index.json`」与「`dist/` 里的包被删或被换」两类问题。

新增插件不需要手工改索引 —— 脚本扫描 `plugins/` 自行发现。

## 3.1 重新签名（改了索引就必须做）

**索引是有签名的，而且客户端会验签。** 因此索引一变，签名就必须跟着变 —— 忘了这一步的
后果不是「新插件看不到」，而是**所有人的市场都打不开**。

```powershell
# 在应用仓库里执行（tauri CLI 在那里）
cd ..\modulith-desktop

# ① 先清掉 TAURI_SIGNING_PRIVATE_KEY。
#
#    这不是可选的：同一个终端里刚跑过 pnpm release / pnpm tauri build 时，它一定还留着
#    （构建链路需要它，值是私钥**路径**），而 signer sign 见到它就会把 -f 当成冲突参数：
#
#      error: the argument '--private-key-path <PRIVATE_KEY_PATH>'
#             cannot be used with '--private-key <PRIVATE_KEY>'
#
#    两者为什么对同一个变量有不同要求，见应用仓库「版本管理」第 7.2.3 节的实测表格。
Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY -ErrorAction SilentlyContinue

# ② -f 不能省：signer 必须知道用哪把私钥。
#    也可以改用 TAURI_SIGNING_PRIVATE_KEY_PATH 环境变量，并复用同一个终端会话。
#    口令来自 TAURI_SIGNING_PRIVATE_KEY_PASSWORD，没设时它会交互式询问。
pnpm tauri signer sign -f "$env:USERPROFILE\.tauri\modulith.key" "..\modulith-plugins\index.json"

# ③ 签完立刻复核：索引比签名新、哈希不符这类问题都会被拦下来
cd ..\modulith-plugins
node scripts/build.ts --check
```

tauri 会把签名写在同名的 `index.json.sig` 里。**把这个文件与 `index.json` 一起提交。**

三点说明：

- **`build.ts` 不会替你签名**，它刻意不接触私钥（它只负责打包与索引）。但它会在写完后
  打印上面这条命令，并且 `--check` 会把「索引改了但没重新签名」当作**错误**拦下来。
- **签名与索引必须同一次提交。** 分开提交意味着中间那一瞬间远端是坏的 —— 而 CDN 不会
  替你等待。
- **签名用的密钥与应用更新是同一把。** 公钥随应用发布（写在应用仓库的
  `src-tauri/tauri.conf.json` 里），因此客户端不需要额外配置。密钥的处置见应用仓库的
  [版本管理](../../modulith-desktop/docs/02-开发指南/版本管理.md)第 7 节。
- **本仓库不做密码学验签。** `--check` 判断「签名是否配套」用的是**文件修改时间比较**
  （`index.json` 比 `.sig` 新就报错）：它只能提醒"改了索引忘了签名"，**不能证明签名有效** ——
  签错文件、用错私钥、签发被截断都发现不了。而真正的验签在客户端
  （`verify_plugin_index`），它一旦失败就是**所有人的市场都打不开**。因此推送前请用**公钥**
  实跑一次验签（`minisign -V` 或 `tauri signer verify`；验签不需要私钥，所以这一步也能放进 CI）。

## 4. 为什么包是确定性的

条目按名称排序，时间戳固定为 1980-01-01，压缩级别固定，压不小就退回不压缩。因此
**同一份源码重复构建得到同一串字节**。

这不是洁癖。索引里记录的 `sha256` 只有在输出确定时才有意义 —— 否则它只能证明「这个包没被
改动过」，不能证明「这个包就是这份源码构建出来的」。

**前提是同一个 Node / zlib 版本。** deflate 的输出由 zlib 实现决定，而脚本的二次打包
比对是**同一进程内**的比较，挡不住版本差异。由于 `--check` 会把「当前源码打包出的哈希
≠ 索引记录」当作错误，换 Node 版本后跑校验可能得到一次**假失败** —— 先确认 Node 版本，
再判断是不是真的改了源码。

**"改了源码忘了升版本"现在会被拒绝。** `build.ts` 在落盘之前检查：若某个版本号已在索引里
存在、而当前源码打包出的哈希不同，直接失败并要求升一个版本。此前这种情况会正常通过，于是
同一个版本号可能出现两份内容 —— 而 README 承诺的「同一个版本号下的内容永远一致」也就只剩
tag 纪律在撑。

脚本每次打包都会**连打两次并比对字节**，因此一旦有人引入时间戳、随机顺序之类的非确定
因素，构建会当场失败，而不是安静地生成一个每次都不一样的包。

## 5. 实际安装一次

不要只看「打包成功」。装一次：

```
设置 > 插件 > 安装插件 > 从插件包安装
```

确认三件事：侧边栏出现模块、模块能操作、**关掉应用重开后状态还在**。第三件事只有真正的
持久化路径能通过，而它恰好最容易被「我以为写了」掩盖。

## 6. 打 tag

每个插件的每个版本一个 tag：

```bash
git tag -a hello-v1.0.0 -m "hello 1.0.0"
```

**已发布的 tag 永不移动、永不删除。** CDN 用 tag 作为缓存键，移动 tag 会让新老用户在同一个
版本号下拿到不同内容 —— 这违反「版本号标识一份确定的内容」这条最基本的约定。改错了就发
一个新版本，不要回头改历史。

## 7. 提交与推送

`index.json` 与 `dist/*.lcp` 都要提交 —— 它们**不在** `.gitignore` 里，这是刻意的，理由见
仓库根 `README.md` 的「为什么同时提交源码与 .lcp」。

```bash
git add -A
git commit -m "chore(release): hello 升至 1.0.1"
git tag -a hello-v1.0.1 -m "hello 1.0.1"
git push origin main --tags
```

## 8. 什么时候跑 --check

```bash
node scripts/build.ts --check
```

它回答的问题是「索引与仓库内容是否还一致」。有用的时候：

- 拉取别人的改动之后，确认索引没有被漏掉重新生成。
- 推送之前（见下）。
- 将来接入 CI 时作为门禁。

**它不只是校验索引与包，还会拦「索引改了但没重新签名」** —— 索引比签名新会返回非零（理由见 3.1）。所以它有两个常见用法，别混起来：

| 时机 | 结果 |
| --- | --- |
| 刚跑完 `build`、**索引确实变了** | 会在签名这一项报错，直到你重新签名 |
| 刚跑完 `build`、索引没变（重复运行） | 全部通过 |

因此它不是「跑完 build 就必然通过」，而是「把打包与签名两件事都核一遍」。刚改完插件就指望它通过，只会看到签名那一项失败 —— 那正是它想告诉你的事。

## 9. 推送之后

- **索引是唯一可变的那一份**，因此它是唯一需要绕缓存的。客户端请求它时带
  `?t=<时间戳>`。
- `.lcp` 走不可变 tag 地址，永久缓存，因此同一个 tag 下的内容永远不会变；README 同理。
- 应用侧的市场页会在下次拉取索引时看到新版本。

### 9.1 `?t=` 保证不了「立刻可见」← 本轮实际遇到过

早先这里写的是「索引走带查询串的地址，应当立刻可见」。**这个说法不成立**，本轮实际
撞上了：仓库里的 `index.json` 是正确的（四个插件都在），而客户端市场里只列出了其中一个。

原因是 `?t=` 只解决「同一份远端内容的不同缓存键」——**如果 CDN 的回源副本本身还停在
旧提交上，换一个查询串也只会拿回同一份旧内容**。查询串让每次请求构成新的缓存键，
但缓存键背后取到的仍是那份没更新的副本。

因此：

```powershell
# 让 CDN 立刻刷新（需要 GitHub 授权；浏览器里打开更省事）
https://purge.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json
https://purge.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json.sig
```

不清也行 —— 分支引用的缓存是若干小时，之后自然会对。但**刚上架时作者和用户都会立刻
去看**，所以他们大概率看到旧索引，表现为「我推上去了，但市场里没有」。清一下省掉一轮
往返。

`.lcp` 与 `README.md` 按不可变 tag 取，**不需要清**。

### 9.2 客户端有两条候选来源

应用的取索引顺序是「jsDelivr → GitHub 直连」；用户配了「下载源」时反过来（GitHub 那条
排前面，并由后端把地址接在加速源域名之后）。因此**两条路都要能取到**，验证方式见
[审核与合并](审核与合并.md) 第 4.2 节。
