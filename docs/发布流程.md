# 发布流程

当前规模下（个位数插件、单一维护者）发布是手工的。自动化 CI 的收益低于它带来的密钥管理
与调试成本，等需要多人投稿时再引入。

> 打包与索引生成的脚本尚未建立。在那之前按本文手工执行；脚本就位后本文会被改写成对脚本
> 的说明，手工步骤随之删除。

## 0. 顺序很重要

```
改版本 → 打包 → 算哈希 → 更新索引 → 提交 → 打 tag → 推送
```

这条顺序里只有一个环节不能颠倒：**打包必须在更新索引之前**。索引记录 `.lcp` 的 `sha256`，
先写索引再打包会得到一个与包不匹配的哈希，而客户端遇到哈希不匹配的表现是「拒绝安装，
文件可能已被篡改」—— 一个由流程错误伪装成的安全告警，排查方向会完全跑偏。

## 1. 发布前检查

- 工作区干净，`main` 已同步。
- 要发布的插件都改过 `manifest.json` 里的 `version`。
- `.lcp` 是从**当前源码**重新打包的，不是上次留下的产物。

最后一条是整条流程里最容易出错的地方。改了源码忘了重新打包，线上包与仓库源码不一致，而
两者看起来都没问题 —— 直到用户报一个你复现不了的 bug。

## 2. 改版本

编辑该插件的 `manifest.json`：

```json
{ "version": "1.0.1" }
```

版本位的选择见[贡献指南](../CONTRIBUTING.md)第 5 节。**新增权限属于 MAJOR** —— 权限变化
会触发用户侧的确认流程，当成小版本会让升级在用户那里显得突然。

## 3. 打包

```powershell
# Windows
Compress-Archive -Path .\plugins\hello\* `
  -DestinationPath .\dist\com.rinntheor.modulith.hello-1.0.1.lcp -Force
```

```bash
# macOS / Linux
cd plugins/hello && zip -r ../../dist/com.rinntheor.modulith.hello-1.0.1.lcp . && cd ../..
```

注意压缩的是目录**内容**而不是目录本身，因此 `manifest.json` 在压缩包根部。多一层目录会
导致安装时找不到清单。

## 4. 算哈希

```powershell
(Get-FileHash .\dist\com.rinntheor.modulith.hello-1.0.1.lcp -Algorithm SHA256).Hash.ToLower()
```

```bash
shasum -a 256 dist/com.rinntheor.modulith.hello-1.0.1.lcp
```

把结果与文件字节数一起写进 `index.json` 对应版本的 `package` 字段。索引格式见应用仓库的
[插件生态设计](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/08-规划/插件生态设计.md) 第 4 节。

## 5. 实际安装一次

不要只看「打包成功」。装一次，确认它能用：

```
设置 > 插件 > 安装插件 > 从插件包安装
```

确认三件事：侧边栏出现模块、模块能操作、**关掉应用重开后状态还在**。第三件事只有真正的
持久化路径能通过，而它恰好是最容易被「我以为写了」掩盖的一环。

## 6. 打 tag

每个插件的每个版本一个 tag：

```bash
git tag -a hello-v1.0.1 -m "hello 1.0.1"
```

**已发布的 tag 永不移动、永不删除。** CDN 用 tag 作为缓存键，移动 tag 会让新老用户在同一个
版本号下拿到不同内容 —— 而这违反的是「版本号标识一份确定的内容」这条最基本的约定。改错了
就发一个新版本，不要回头改历史。

## 7. 推送

```bash
git push origin main --tags
```

## 8. 推送之后

- 索引走 jsDelivr 的带查询串地址，应当立刻可见（查询串让每次请求构成不同的缓存键）。
- `.lcp` 走不可变 tag 地址，永久缓存，因此**同一个 tag 下的内容永远不会变**。
- 应用侧的市场页会在下次拉取索引时看到新版本。

若索引长时间不更新，先确认它确实是带查询串请求的 —— 这一点需要真实网络环境验证，见应用
仓库设计文档第 12 节的未决问题。
