# 插件目录规范

本仓库中每个插件占据 `plugins/<短名>/` 一个目录。本文是该结构的权威定义。

## 1. 必需与可选文件

| 文件 | 必需 | 说明 |
| --- | --- | --- |
| `manifest.json` | 是 | 清单：身份、版本、入口、权限 |
| `index.js` | 是 | 代码包：手写 IIFE，或由 `src/<目录名>/` 构建而来（见第 2 节）。实际路径由 `main` 决定，本仓库统一为根目录下的 `index.js` |
| `README.md` | 是 | 会显示在应用的插件详情抽屉里，面向**使用者**而非开发者 |
| `LICENSE` | 是 | 本插件的许可证全文 |
| `index.css` | 否 | 样式，需在清单声明 `style` |
| `icon.svg` | 否 | 图标，需在清单声明 `icon` |

`README.md` 与 `LICENSE` **应用侧不强制** —— 缺少它们不会导致安装被拒（唯一例外是 README 缺失时详情页会显示一句「该版本的仓库里没有 README.md」）。**但本仓库的构建脚本强制**：`scripts/manifest.ts` 的 `REQUIRED_FILES` 是 `manifest.json` / `index.js` / `README.md` / `LICENSE`，缺任何一个 `node scripts/build.ts` 都会失败。

两层要求并不矛盾，只是层次不同：应用只要求「装得上」，本仓库要求「上架的东西是完整可读的」。这两份文件服务于读者 —— 一个是装了插件的人，一个是想知道「我能不能用、能不能改」的人。缺了它们，插件在详情抽屉里就是一片空白。

### 1.1 `README.md` 是这个插件的用户可见页面

**改动 `README.md` 或 `LICENSE` 等于改动已发布的包。** 它们与 `index.js` 一样是 `.lcp` 的内容（`scripts/manifest.ts` 的 `REQUIRED_FILES` 把四者一并要求、一并打包），因此：

- 改完之后 `node scripts/build.ts --check` 会报「源码当前打包出的哈希与索引记录不符」—— 这不是误报，线上包确实与仓库源码不一致了；
- 正确处理是**走一次完整的发版**：升 PATCH 版本 → 重新打包 → 重新生成索引 → 重新签名 → 打新 tag。改文案属于 PATCH（见 `CONTRIBUTING.md` 第 5 节）；
- **不要**只改 README 就提交。那时索引里的哈希对不上包，客户端安装会在哈希校验处失败 —— 而 README 的措辞问题远不值得这个代价。

同理，`README.md` 不是「附带文件」，而是**用户在两个地方实际读到的内容**：

| 位置 | 时机 | 内容来源 |
| --- | --- | --- |
| 设置 → 市场 → 详情 | **安装之前** | 该版本 tag 下的 `plugins/<名称>/README.md` |
| 设置 → 插件 → 详情 | 安装之后 | 安装包内的 `README.md` |

两点推论：

- **它是你唯一的"描述内容"。** 索引里只有一个列表用的一句话
  （来自清单的 `description`），长说明一律来自这个文件。想改详情页，就改这个文件 ——
  不需要改任何配置，也不会出现"配置里写的"和"README 里写的"不一致。
- **写给人看，不是写给人查。** 列表里那一句负责让人决定"要不要点进来看"，README 负责
  让人决定"要不要装"。功能、取舍、以及它需要哪些权限、这些权限用来做什么，都在这里说清楚。

**1.1.8 起按 Markdown 渲染**：标题、列表、表格、围栏代码块、行内代码、粗体与链接
都会正常显示，市场详情与已安装插件详情走**同一个渲染器**。此前那句「当前版本以纯文本
展示，不渲染 Markdown 语法」已经过时。

两条仍然成立的约束（它们是渲染器的安全设计，不是待办）：

- 链接一律交给**系统浏览器**打开，不在应用内跳转 —— 否则点一下说明里的链接会把整个
  应用界面替换掉；
- 图片**不会自动加载**，只显示为可点击的链接 —— 直接渲染 `<img>` 等于让「打开插件详情」
  这个动作隐式向第三方主机发一次请求。

## 2. 两条路：手写单文件，或从 `src/` 构建

`index.js` 有两个来源，而**产物完全一样** —— 宿主只要求清单的 `main` 指向一个可执行的
JS 文件，它不关心那是怎么来的。

**手写单文件（默认，门槛最低）。** `index.js` 就是手写源码，直接被打进 `.lcp`。仓库里
大多数插件走这条路。好处是「仓库里的文件」与「用户装到的文件」逐字节相同，任何人
`git checkout` 某个 tag 就能核对线上包的内容。代价是不能写 JSX，只能用
`React.createElement`（简写为 `h`）。

**从 `src/<目录名>/` 构建（快车道，可选）。** 源码写在**仓库根**的 `src/<目录名>/`，可以
拆成多个文件、可以写 JSX 与 TypeScript，`node scripts/build.ts` 把它编译成
`plugins/<目录名>/index.js`。详见 [src/README.md](../src/README.md)。

两条路并存而不冲突的理由：产物仍是**单文件 IIFE**，与手写时完全一样，因此打包 zip 与生成
索引的流程一个字都没改。`node scripts/build.ts --check` 会重新编译一遍并与磁盘上的产物
比对，源码改了却忘了构建会被当场拦下来。

两点容易搞混，写在这里：

- **源码在仓库根的 `src/<目录名>/`，不是 `plugins/<目录名>/src/`。** 插件目录里只有清单、
  资源与产物。
- **产物始终是 `plugins/<目录名>/index.js`** —— 与手写时同名同位置，所以 `main` 不需要改，
  `.lcp` 的结构也不变。

从这条快车道产出的 `index.js` 首行有一句「生成物，请勿手改」的 banner。手写插件的
`index.js` 没有这一行，构建脚本也据此区分「产物」与「手写源码」（判断孤立产物时用）。

## 3. 命名规则

| 对象 | 规则 | 强制程度 | 示例 |
| --- | --- | --- | --- |
| 目录名 | 小写字母、数字与 `-`，**在本仓库内唯一** | **硬要求** | `hello` |
| 插件 ID（`name`） | 反向域名，1 至 64 字符，首字符为字母或数字 | 硬要求，且**发布后不可更改** | `com.rinntheor.modulith.hello` |
| 版本 tag | `<目录名>-v<版本号>` | 硬要求（由脚本推出来，不手写） | `hello-v1.0.0` |
| 目录名与 ID 末段一致 | 例如 `plugins/hello` ↔ `...modulith.hello` | **建议**（见下） | — |

插件 ID 同时是**安装目录名**与**数据存储命名空间**，因此一旦发布就**不可更改**。改名会让
老用户的数据失去归属，也会让已安装的旧版本与新版本被当成两个不同的插件。

### 3.1 目录名与 ID 末段一致：从硬规则降级为建议

从前这条是**错误**：`scripts/manifest.ts` 会直接拦下目录名与 ID 末段不一致的插件。现在它
只是一句建议（`namingAdvisories`，只打印、不阻断构建），因为硬要求其实只有一个：
**目录名在本仓库内唯一**。

**为什么解耦是安全的 —— 全链路只看目录名，不看 ID 末段：**

| 环节 | 用的是哪一个 | 说明 |
| --- | --- | --- |
| 版本 tag | **目录名** | `tag: \`${dirName}-v${version}\``（`scripts/build.ts` 的 `packOne`）。tag 是 CDN 的永久缓存键，也是「版本号 = 一份确定的内容」的唯一凭据；它只要求目录名不重复 |
| 索引里的 `source` / `icon` | **目录名** | `plugins/<目录名>`，客户端按它取该 tag 下的 README 与图标 |
| 产物落点 | **目录名** | 新布局是 `dist/<目录名>/<版本号>.lcp` |
| 安装目录与数据命名空间 | **插件 ID** | 与目录名叫什么毫无关系 |

因此 `plugins/b-notes/` 里装一个 ID 为 `com.b.modulith.notes` 的插件，在 tag、索引、
产物路径、安装、数据存储这五条链路上都没有任何一步会失败。

**冲突由反向域名 ID 化解，而不是由目录名化解。** 这是 ID 用反向域名的意义所在：
两个人都能做笔记插件 —— `com.a.modulith.notes` 与 `com.b.modulith.notes` 是两个互不
冲突的插件，连 `displayName` 都可以都叫「笔记」，用户看到的是两个作者各自的「笔记」。
把规则绑死在 ID 末段上的代价恰好相反：第二个人必须改目录名，于是被迫改 ID
（`com.b.modulith.notes-b`），作者信息在名字里重复了一遍。

仍然建议两者一致，理由是**人对照方便**：读 `plugins/hello` 就知道 `...modulith.hello`
是它。要带作者前缀也可以（`plugins/b-notes` ↔ `com.b.modulith.notes`）—— 名字里有作者
是这种做法的自然结果，而不是错误。

## 4. 清单要点

完整字段说明见应用仓库的
[清单文件参考](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/02-开发指南/插件开发/清单文件参考.md)。
本仓库有两条额外要求。

### 4.1 `engines.modulith` 只写下界

下限写**插件真正需要的那个版本**，而不是习惯性的 `>=1.0.0` —— 后者会让更旧的宿主
**收不到任何提示**，而"需要提示"正是它的用途。本仓库当前的分法是**按插件实际用到的
宿主能力**分开的。

**实测（逐个读 `plugins/*/manifest.json`，本仓库现有 11 个插件全部 `runtime: "sandboxed"`）：**

| 插件 | `engines.modulith` | 为什么 |
| --- | --- | --- |
| `art-trace` | `>=1.6.3` | 它声明并使用了 `filesystem-scoped`（`ctx.files`）：**用户在原生对话框里当场授权的目录**。那条通道是 1.6.3 才落地的（宿主仓库 `docs/08-规划/插件沙箱与数据-v2.0范围.md` 记着它"已实现（1.6.3 的 `ctx.files`）"） |
| 其余 10 个（`hello`、`notes`、`pomodoro`、`quick-launch`、`stand-up`、`kanban`、`color-lab`、`encode-lab`、`regex-lab`、`typing-practice`） | `>=1.6.0` | 沙箱运行时、以及宿主送进插件文档的那一份 React，都是 1.6.0 才有的 |

> **这张表此前写的是「hello 是沙箱，其余 8 个仍是 in-process、下限 `>=1.2.0`」—— 已经
> 过时。** 沙箱迁移完成后 11 个插件全部是 `runtime: "sandboxed"`，一条 `>=1.2.0` 都没有了。

**下界与运行位置是耦合的：迁移到沙箱时必须同时抬下限。** 一个插件不可能"跑在沙箱里"
却声明兼容 1.2.0 —— 那样的宿主不会给出任何提示，然后在里面跑不起来。

只带下界（而不是 caret）的理由：caret 在 1.0 之后等价于 `>=x.y.z <(x+1).0.0`，
宿主升到大版本时会给所有插件挂上一条兼容性提示，而那条提示对用户没有实际价值 ——
插件到底兼不兼容由它的代码决定，真的不兼容时加载会失败并显示原因。

### 4.2 `permissions` 只写真正用到的

权限列表是给用户看风险用的，**多写一项就多一分误导**。审查会核对声明与代码里实际调用的
宿主接口是否一致。

`plugins/hello` 只声明一项 `storage`，这本身就是个值得记住的结论：多数插件不需要申请
危险权限。

## 5. 三条硬性禁止

### 5.1 权限名不能用冒号写法

```jsonc
"permissions": ["filesystem:read"]   // 错误：整份清单反序列化失败，安装被拒
```

权限名是小写 kebab-case 枚举，取值以宿主提供的注册表为准。完整清单、每项的推导风险等级
与"当前是否强制"，权威来源有两处，都在应用仓库：

- [清单文件参考](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/02-开发指南/插件开发/清单文件参考.md) 第 4 节 —— 面向作者的完整取值表；
- `src-tauri/src/modules/plugins/permissions.rs` —— 真正实现，权限注册表的唯一定义处
  （`list_plugin_permissions` 命令就是它暴露出来的）。

> **这里此前指向 `docs/08-规划/插件生态设计.md` 第 3 节，那份文件已在 1.3.2 周期删除，
> 引用因此失效。** 按仓库自己的规矩，失效的引用要么修好要么删掉 —— 上面两处是现存且
> 权威的替代。

写错一个权限名不会得到「未知权限」的提示，而是**整份清单解析失败**。这个失败方式的代价
比看起来大：用户看到的是「清单非法」，而原因只是多打了个冒号。

### 5.2 不能用 Tailwind 工具类

Tailwind 是在**构建宿主时**扫描宿主源码生成类名的。插件在运行时才注入，它写的 `bg-white`
不在那次扫描范围内，因此**不会生成对应规则** —— 类名存在，但没有任何样式生效。

结果是一个只在你机器上看起来正常的插件（如果你本地恰好有别的样式表覆盖了它），在用户那里
完全走样。

插件的样式写在自己的 `index.css` 里：

- 类名加插件专属前缀，避免与宿主或其他插件冲突。
- 颜色复用宿主的 `--accent-*` 变量，并带兜底值。
- 为 `:root.dark` 补一份深色样式，否则深色模式下会得到一片浅色方块。

> **`plugins/hello` 的 1.0.3 及更早版本是这两条的反例 —— 别照抄那一份。** 它用
> `prefers-color-scheme` 判断深色并自己带颜色，文件头还写着「沙箱里宿主变量与
> `.dark` 都不存在」—— 那是 1.6.0 之前的结论，现在**相反**：宿主会把全套设计令牌
> 注入插件文档，并在插件文档自己的 `:root` 上挂 `.dark`。
>
> 用 `prefers-color-scheme` 的写法**不会跟随宿主的主题开关**（系统深色 + 应用浅色
> 是最常见的组合，那时插件不动，看起来像插件坏了）。要抄骨架就抄 `plugins/notes`
> 或 `plugins/color-lab`，或者抄 `hello` 的 **1.0.4**（该版本已改为 `:root.dark`）。

### 5.3 不能提交 `node_modules` 或构建缓存

插件是单文件 IIFE，没有运行时依赖。任何「这个插件需要先 npm install」的情况都说明设计错了：
宿主不会为用户执行安装步骤。

## 6. `.lcp` 的内部结构

`.lcp` 是一个 zip 容器，扩展名用于标识与文件选择过滤。打包时压缩的是插件目录的**内容**
而不是目录本身，因此 `manifest.json` 位于压缩包**根部**：

```
dist/hello/1.0.4.lcp        ← 包的文件名与布局无关，下面是它的**内部**结构
├── manifest.json
├── index.js
├── index.css
├── icon.svg
├── README.md
└── LICENSE
```

如果多了一层目录，安装时会找不到清单。产物统一放在仓库根的 `dist/`，而那里**有两种
形状**（见 `dist/README.md`）：

```
dist/<插件目录名>/<版本号>.lcp          ← 新版本（脚本现在生成的就是这个）
dist/<插件 ID>-<版本号>.lcp             ← 历史版本，平铺，**路径不可改**
```

历史版本的那一种不能动：索引里的 `package.path` 是客户端直接拼接的下载地址，而旧 tag 的
提交树里文件就在平铺路径上 —— 改路径会让老用户 404。详见 `dist/README.md`。
