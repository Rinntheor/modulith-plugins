# 插件目录规范

本仓库中每个插件占据 `plugins/<短名>/` 一个目录。本文是该结构的权威定义。

## 1. 必需与可选文件

| 文件 | 必需 | 说明 |
| --- | --- | --- |
| `manifest.json` | 是 | 清单：身份、版本、入口、权限 |
| `index.js` | 是 | 代码包，手写 IIFE。实际路径由 `main` 决定，本仓库统一为根目录下的 `index.js` |
| `README.md` | 是 | 会显示在应用的插件详情抽屉里，面向**使用者**而非开发者 |
| `LICENSE` | 是 | 本插件的许可证全文 |
| `index.css` | 否 | 样式，需在清单声明 `style` |
| `icon.svg` | 否 | 图标，需在清单声明 `icon` |

`README.md` 与 `LICENSE` **应用侧不强制** —— 缺少它们不会导致安装被拒（唯一例外是 README 缺失时详情页会显示一句「该版本的仓库里没有 README.md」）。**但本仓库的构建脚本强制**：`scripts/manifest.ts` 的 `REQUIRED_FILES` 是 `manifest.json` / `index.js` / `README.md` / `LICENSE`，缺任何一个 `node scripts/build.ts` 都会失败。

两层要求并不矛盾，只是层次不同：应用只要求「装得上」，本仓库要求「上架的东西是完整可读的」。这两份文件服务于读者 —— 一个是装了插件的人，一个是想知道「我能不能用、能不能改」的人。缺了它们，插件在详情抽屉里就是一片空白。

### 1.1 `README.md` 是这个插件的用户可见页面

**改动 `README.md` 或 `LICENSE` 等于改动已发布的包。** 它们与 `index.js` 一样是 `.lcp` 的内容（`scripts/manifest.ts` 的 `REQUIRED_FILES` 把四者一并要求、一并打包），因此：

- 改完之后 `node scripts/build.ts --check` 会报「源码当前打包出的哈希与索引记录不符」—— 这不是误报，线上包确实与仓库源码不一致了；
- 正确处理是**走一次完整的发版**：升 PATCH 版本 → 重新打包 → 重新生成索引 → 重新签名 → 打新 tag。改文案属于 PATCH（见 `CONTRIBUTING.md` 第 5 节）；
- **不要**只改 README 就提交。那时索引里的哈希对不上包，客户端安装会在哈希校验处失败 —— 而 README 的措辞问题远不值得这个代价。

同理，`README.md` 不是「附带文件」，而是**用户在两个地方实际读到的内容**：

| 位置 | 时机 | 内容来源 |
| --- | --- | --- |
| 设置 → 市场 → 详情 | **安装之前** | 该版本 tag 下的 `plugins/<名称>/README.md` |
| 设置 → 插件 → 详情 | 安装之后 | 安装包内的 `README.md` |

两点推论：

- **它是你唯一的"描述内容"。** 索引里只有一个列表用的一句话
  （来自清单的 `description`），长说明一律来自这个文件。想改详情页，就改这个文件 ——
  不需要改任何配置，也不会出现"配置里写的"和"README 里写的"不一致。
- **写给人看，不是写给人查。** 列表里那一句负责让人决定"要不要点进来看"，README 负责
  让人决定"要不要装"。功能、取舍、以及它需要哪些权限、这些权限用来做什么，都在这里说清楚。

**当前版本以纯文本展示**，不渲染 Markdown 语法 —— 与你看到的已安装插件详情保持一致。
因此标题、表格这类结构仍然可读（原本就是对齐的），但 `**粗体**` 会原样显示。

## 2. 为什么没有构建步骤

应用侧的[快速开始](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/02-开发指南/插件开发/快速开始.md)
使用 `dist/index.js`，因为那里假定你用了打包器。**本仓库的插件不使用构建步骤**：
`index.js` 就是手写源码，直接被打进 `.lcp`。

好处是「仓库里的文件」与「用户装到的文件」逐字节相同，任何人 `git checkout` 某个 tag
就能核对线上包的内容。代价是不能写 JSX，只能用 `React.createElement`。

如果某个插件确实需要打包器（例如要用 TypeScript），把源码放该插件下的 `src/`、产物放
插件根目录，并在该插件的 `README.md` 里写明构建步骤。**不要让产物与源码同名混淆。**

## 3. 命名规则

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 目录名 | 小写字母、数字与 `-`，在本仓库内唯一 | `hello` |
| 插件 ID（`name`） | 反向域名，1 至 64 字符，首字符为字母或数字 | `com.rinntheor.modulith.hello` |
| 版本 tag | `<目录名>-v<版本号>` | `hello-v1.0.0` |

插件 ID 同时是**安装目录名**与**数据存储命名空间**，因此一旦发布就**不可更改**。改名会让
老用户的数据失去归属，也会让已安装的旧版本与新版本被当成两个不同的插件。

目录名与插件 ID 的最后一段保持一致，便于人对照（`plugins/hello` ↔ `...modulith.hello`）。

## 4. 清单要点

完整字段说明见应用仓库的
[清单文件参考](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/02-开发指南/插件开发/清单文件参考.md)。
本仓库有两条额外要求。

### 4.1 `engines.loopcore` 只写下界

写 `>=1.0.0`，不要写 `^1.0.0`。

两者都能匹配 1.x，但 caret 在 1.0 之后等价于 `>=1.0.0 <2.0.0`：宿主升到 2.0 时会给所有
插件挂上一条兼容性提示，而那条提示对用户没有实际价值 —— 插件到底兼不兼容由它的代码决定，
真的不兼容时加载会失败并显示原因。

### 4.2 `permissions` 只写真正用到的

权限列表是给用户看风险用的，**多写一项就多一分误导**。审查会核对声明与代码里实际调用的
宿主接口是否一致。

`plugins/hello` 只声明一项 `storage`，这本身就是个值得记住的结论：多数插件不需要申请
危险权限。

## 5. 三条硬性禁止

### 5.1 权限名不能用冒号写法

```jsonc
"permissions": ["filesystem:read"]   // 错误：整份清单反序列化失败，安装被拒
```

权限名是小写 kebab-case 枚举，取值以宿主提供的注册表为准。完整清单与各自的推导风险等级见
应用仓库的[插件生态设计](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/08-规划/插件生态设计.md)
第 3 节。

写错一个权限名不会得到「未知权限」的提示，而是**整份清单解析失败**。这个失败方式的代价
比看起来大：用户看到的是「清单非法」，而原因只是多打了个冒号。

### 5.2 不能用 Tailwind 工具类

Tailwind 是在**构建宿主时**扫描宿主源码生成类名的。插件在运行时才注入，它写的 `bg-white`
不在那次扫描范围内，因此**不会生成对应规则** —— 类名存在，但没有任何样式生效。

结果是一个只在你机器上看起来正常的插件（如果你本地恰好有别的样式表覆盖了它），在用户那里
完全走样。

插件的样式写在自己的 `index.css` 里：

- 类名加插件专属前缀，避免与宿主或其他插件冲突。
- 颜色复用宿主的 `--accent-*` 变量，并带兜底值。
- 为 `:root.dark` 补一份深色样式，否则深色模式下会得到一片浅色方块。

### 5.3 不能提交 `node_modules` 或构建缓存

插件是单文件 IIFE，没有运行时依赖。任何「这个插件需要先 npm install」的情况都说明设计错了：
宿主不会为用户执行安装步骤。

## 6. `.lcp` 的内部结构

`.lcp` 是一个 zip 容器，扩展名用于标识与文件选择过滤。打包时压缩的是插件目录的**内容**
而不是目录本身，因此 `manifest.json` 位于压缩包**根部**：

```
com.rinntheor.modulith.hello-1.0.0.lcp
├── manifest.json
├── index.js
├── index.css
├── icon.svg
├── README.md
└── LICENSE
```

如果多了一层目录，安装时会找不到清单。产物统一放在仓库根的 `dist/`，文件名为
`<插件 ID>-<版本号>.lcp`。
