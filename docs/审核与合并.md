# 审核与合并（维护者流程）

本文写给**持有签名私钥的维护者**：收到一个插件的 PR 之后，从审核到它在用户市场里出现，中间要做哪些事、按什么顺序。

## 0. 先看一件事：现在是否该收这个 PR

`CONTRIBUTING.md` 第 1 节写明了当前状态：**插件权限是声明式的，拦不住恶意插件**。插件代码与宿主界面在同一个 JavaScript 上下文里，一个声明「我只读剪贴板」的插件照样能调用宿主暴露的一切。要真正隔离需要 Web Worker / iframe / 独立进程加一套 RPC 协议，成本是改造全部现有插件。

所以顺序是：先把自己的插件与分发链路跑通，等真的收到投稿请求时再做沙箱。

**这条直接决定了审核的性质：**

| 情形 | 该怎么办 |
| --- | --- |
| 陌生人的 PR | 先按 `CONTRIBUTING.md` 第 1 节回复：投稿流程尚未开放，原因是权限模型还拦不住恶意代码。**不要因为代码看起来干净就合并** —— 当前模型下你无法通过阅读一次性确认它此后不会变（作者随时能发新版本） |
| 你信任的人（或你自己的另一个账号）的 PR | 按本文流程走。审核的重点从「防恶意」转成「防错误」 |
| 沙箱落地之后 | 本文的流程仍然是主干，但审核标准需要按 `CONTRIBUTING.md` 的更新重写 |

本文以下内容假设**已经决定收这个 PR**。

## 1. 不要先在 PR 分支上签名

这是最容易做错的一步，先理解原因再动手：

`index.json` 由 `scripts/build.ts` **扫描工作区生成**。PR 分支上的索引反映的是那个分支的状态，而合并之后 `main` 上可能有别的插件的改动（别人的上架、你自己的版本升级）。**签名是给一份具体字节签的**，在合并前的索引上签名，合并后必然对不上 —— 而客户端的表现不是「新插件看不到」，是**所有人的市场都打不开**（验签失败会拒绝整份索引）。

所以顺序是：**先合并 → 再生成索引 → 再签名**。

## 2. 审核清单

```bash
git fetch origin pull/<PR号>/head:pr-<PR号>
git checkout pr-<PR号>
```

### 2.1 结构

| 检查项 | 要求 |
| --- | --- |
| 目录位置 | `plugins/<目录名>/`，目录名与插件 ID 末段一致 |
| `manifest.json` | 字段完整；`name` 是反向域名式 ID |
| `README.md` | **必须存在** —— 市场详情页显示的正文就是它（按不可变 tag 取该版本的说明） |
| `LICENSE` | **必须存在** —— 它回答「我能不能用这个插件」 |
| `index.js` | IIFE。**界面型**在顶层调用 `registerModule()`；**功能型**调用 `registerCommand()`，或什么都不注册、只在清单里声明 `activationEvents` |
| `icon.svg` | 建议有；没有则市场里显示通用图标 |
| `dist/<插件ID>-<版本>.lcp` | 已在 PR 里，且**与源码一致**（见 2.4） |

完整规则与理由见[目录规范](目录规范.md)。

**1.2.0 起，插件不再必须是一个侧边栏模块。** 清单里的 `contributes` 与
`activationEvents` 让宿主在**没有执行任何插件代码**时就建立完整的界面目录，因此
「只加几条命令」「只在后台监听」「只提供一组设置项」都成了合法形态。此前这些插件
会被判为加载失败 —— 审核清单里那句「顶层同步调用 `registerModule()`」正是那个旧判据，
已按代码事实改掉。

审核**按形态给验收方式**：

| 形态 | 怎么验 |
| --- | --- |
| 界面型（`contributes.modules` 非空） | 打开那个模块，界面正常 |
| 命令型 | 命令面板（Ctrl+K）里搜得到，执行有反应 |
| 设置型 | 设置 →「插件设置」里出现它，改了值插件读得到 |
| 后台型（`contributes: {}` + `onStartup`） | **没有界面可看** —— 改为核对两件事：触发时机是不是它声明的那一个；以及它创建的资源是否**都登记了收尾**（见下） |

**功能型插件必须登记收尾。** 后台服务创建的定时器、事件监听、观察者、网络连接，
**宿主一个都不知道** —— 不登记就会在插件被禁用之后继续留在后台。用
`ctx.disposables.add(...)` 或 `Modulith.onDeactivate(...)` 交出去。
**这一条对界面型插件几乎用不到，对功能型插件是硬要求**，审核时逐条核对。

（`ctx.disposables` 是 1.2.0 才有的东西。换句话说：**在 1.2.0 之前，功能型插件
根本没法被正确写出来** —— 写了就会泄漏。这条要求与那个能力是同一次改动。）

### 2.2 ID 是否被占用

```bash
grep -n '"id"' index.json
```

**已在索引里出现过的 ID + 换了作者或换了实现 → 停下来问清楚。** ID 一旦发布不可更改（它同时是安装目录名与数据存储命名空间），换一个 ID 是新增插件，占同一个 ID 是劫持老用户的安装。

### 2.3 版本号

```bash
git show origin/main:index.json | grep -A2 '"id": "com.example.my-plugin"'
```

- 新插件从 `1.0.0` 起（首次提交写成 `1.0.1` 要问一句：索引里出现「首个版本是 1.0.1」会让读者以为漏了一版）；
- 已有插件的新版本必须**大于**索引里的 `latest`，不能重号；
- **新增权限属于 MAJOR**（`CONTRIBUTING.md` 第 5 节）—— 权限变化会触发用户侧的确认流程，当成小版本会让升级在用户那里显得突然。

### 2.4 `.lcp` 与源码是否一致 ← 必须亲手验一次

「改了源码忘了重新打包」是最常见的 PR 问题，而且症状是**用户装到的还是旧代码**，作者本地用「从文件夹安装」（dev-linked）测试时完全看不出来。

```powershell
$id = 'com.example.my-plugin'; $ver = '1.0.0'; $dir = 'my-plugin'
Remove-Item -Recurse -Force $env:TEMP\lcp-check -ErrorAction SilentlyContinue
Expand-Archive "dist\$id-$ver.lcp" -DestinationPath $env:TEMP\lcp-check
Get-ChildItem $env:TEMP\lcp-check -Recurse -File | ForEach-Object {
  $rel = $_.FullName.Replace("$env:TEMP\lcp-check\", '')
  $src = "plugins\$dir\$rel"
  if (-not (Test-Path $src)) { "包里多出来的文件: $rel" }
  elseif ((Get-FileHash $_.FullName).Hash -ne (Get-FileHash $src).Hash) { "内容不一致: $rel" }
}
Remove-Item -Recurse -Force $env:TEMP\lcp-check
```

顺带确认 `manifest.json` **位于包根部**（上一步的输出里应当直接看到它，而不是 `my-plugin\manifest.json`）。

### 2.5 权限的必要性 ← 审核的真正重点

```bash
grep -n 'permissions' -A10 plugins/<目录名>/manifest.json
```

逐条对照代码确认「声明的」与「实际调用的」一致，并且**每一项都必要**。权限列表是用户唯一能看到的东西 —— 它是给用户看风险用的，多写一项就多一分误导。

| 权限 | 意味着 | 要问的问题 |
| --- | --- | --- |
| `storage` | 能读写自己的键值存储 | 存的是不是敏感信息 |
| `notification` | 能发应用内通知 | — |
| `plugin-communicate` | 能与其他插件收发事件 | 会广播什么 |
| `network` | 能经由宿主代发 HTTP 请求 | 往哪发、发什么 |
| `network-external` | 能访问任意外部地址 | 同上，且范围更大 |
| `filesystem-read` | 能读本机文件 | 读哪些路径？路径是写死的还是用户输入的？会不会扫目录 |
| `process-spawn` | 能启动本机任意程序 | 启动什么？参数从哪来 |
| （服务名，不是权限名） | `ctx.launcher` → `process-spawn`；`ctx.icons` / `ctx.shell` / `ctx.fileDrop` / `ctx.audio` → `filesystem-read` | 核对代码里调用的服务，是否都有对应的权限声明 |

**能少则少。** 一个只发通知的插件不该要 `filesystem-read`。

**权限名以宿主的权限注册表为权威来源**（`list_plugin_permissions` 命令，实现见应用仓库
`src-tauri/src/modules/plugins/permissions.rs`）。本仓库不维护第二份名单 —— 上表此前把
`launcher` / `icons` / `audio` 列为权限名，那三个其实是**服务名**；照它核对会让人给插件
多报权限，正好违反本节自己的要求。

### 2.6 代码

没有自动化扫描能替代通读一遍。重点看：

- `eval` / `new Function` / 拼接字符串后执行；
- 把用户输入直接拼进 URL、命令、文件路径；
- 往可疑地址发送数据；
- `setInterval` / `setTimeout` 有没有配合 `useModuleActive()`（否则标签切走后仍在跑，用户感知是「卡」）；
- 样式有没有用 Tailwind 工具类（宿主构建期生成类名，插件运行时注入的类名不会被生成 —— 见 `CONTRIBUTING.md` 第 2 节）。

### 2.7 索引与产物的一致性

```bash
node scripts/build.ts --check
```

它校验「索引引用的每个包都存在，且哈希与记录一致」。这一步在 PR 分支上可能就已经通过 —— 但**它不能替代第 3 节的重新生成**，原因见第 1 节。

## 3. 合并之后：重新生成、签名、打 tag

### 3.1 合并

```bash
git checkout main && git pull
git merge --no-ff pr-<PR号> -m "feat(<插件目录名>): 引入 XXX 插件（PR #<PR号>）"
```

用 merge commit 而不是 squash：保留作者的提交与署名。

### 3.2 重新生成索引

```bash
node scripts/build.ts
git diff index.json
```

**期望的差异只有这个插件的那几行**（新增条目，或已有插件多一个版本条目）。

**如果看到别的插件的 `sha256` 也变了，停下来。** 那意味着有其他包被改动过，而这次上架里不该有那种改动。

```bash
node scripts/build.ts --check   # 复核：每个包都存在且哈希一致
```

### 3.3 看一眼索引内容

```bash
node -e "const i=require('./index.json');const p=i.plugins.find(x=>x.id==='com.example.my-plugin');console.log(JSON.stringify(p,null,2))"
```

确认：`latest` 是你同意上架的版本、`versions[].tag` 是 `<目录名>-v<版本>`、`permissions` 是你审核通过的那一组、`package.sha256` 是脚本算出来的（不是你手写的）。

### 3.4 签名

```powershell
# 清掉可能残留的变量：同一个终端里刚跑过 pnpm release / tauri build 时它一定还在，
# 而 signer sign 见到它就会把 -f 当成冲突参数（见 docs/发布流程.md 第 3.1 节）
Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY -ErrorAction SilentlyContinue

cd ..\modulith-desktop
pnpm tauri signer sign -f "$env:USERPROFILE\.tauri\modulith.key" "..\modulith-plugins\index.json"
```

**验证签名确实换了：**

```bash
cd ../modulith-plugins
git diff --stat index.json index.json.sig
```

两个文件都应当有变化。`index.json.sig` 没变说明索引一个字节都没动 —— 回到 3.2 查。

### 3.5 提交、打 tag、推送

```bash
git add index.json index.json.sig
git commit -m "chore(index): 重新生成并签名索引（含 com.example.my-plugin 1.0.0）"

# tag 必须存在，而且必须指向包含这个 .lcp 的提交
git tag -a <目录名>-v<版本> -m "<插件名> <版本>"
git push origin main
git push origin <目录名>-v<版本>
```

**索引单独一个提交**：这样「那一次上架改了什么」在历史里是一条独立记录，而不是混在合并提交里看不出来。

**`index.json` 与 `index.json.sig` 必须在同一个提交里**（`docs/发布流程.md` 第 3.1 节）：分开提交意味着中间那一瞬间远端是坏的，而 CDN 不会替你等待。

**验证 tag 指向正确：**

```bash
git ls-remote --tags origin | grep <目录名>
git rev-parse <目录名>-v<版本>   # 应当等于 git rev-parse HEAD
```

tag 不在 `HEAD` 上（比如包在更早的提交里）就用 `git tag -f -a <名> <正确的哈希>` 重打并强推。**已发布的 tag 永不移动**，但打错的 tag 在推送前改正不算发布。

## 4. 推送之后

### 4.1 索引可见性（这里有一个已实际遇到的坑）

`docs/发布流程.md` 第 9 节原先说「索引走 jsDelivr 的带查询串地址，应当立刻可见」。**本轮实际遇到的现象与它不符**：仓库里的索引是正确的（四个插件都在），而客户端市场里只列出了其中一个。

索引请求带 `?t=<时间戳>` 只能绕开「同一份远端内容的不同缓存键」；**如果 CDN 的回源副本本身还停在旧提交上，换查询串也只会拿回同一份旧内容**。因此不要依赖查询串保证可见性。

```powershell
# 让 CDN 立刻刷新（需要 GitHub 授权，浏览器里打开更省事）
https://purge.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json
https://purge.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json.sig
```

不清也行，缓存是若干小时。但**刚上架时作者和用户都会立刻去看**，所以他们大概率看到旧索引，表现为「推上去了但市场里没有」。清一下省掉一轮往返。

`.lcp` 与 `README.md` 按**不可变 tag** 取，内容永不变，CDN 永久缓存是最优解 —— 它们不需要清。

### 4.2 从用户视角验证一遍

```powershell
# 仓库侧：索引里确实有新插件
git show origin/main:index.json | Select-String '<插件ID>'

# 两个候选来源都能取到（应用会按顺序尝试它们）
(Invoke-RestMethod 'https://raw.githubusercontent.com/Rinntheor/modulith-plugins/main/index.json').plugins.id
(Invoke-RestMethod 'https://cdn.jsdelivr.net/gh/Rinntheor/modulith-plugins@main/index.json').plugins.id

# 包能被下载（HEAD 返回 200）
Invoke-WebRequest 'https://cdn.jsdelivr.net/gh/Rinntheor/modulith-plugins@<tag>/dist/<插件ID>-<版本>.lcp' -Method Head
```

然后在**干净的应用实例**里（或先卸载该插件）走一遍：设置 → 市场 → 刷新 → 找到插件 → 详情页 README 正常显示（不是空白）→ 安装 → 权限列表与索引里的一致 → 装完能用 → 关掉应用重开后状态还在。

最后一条只有真正的持久化路径能通过，而它最容易被「我以为写了」掩盖。

## 5. 审核不通过时怎么回

在 PR 上写清**具体哪一条**，不要只说「不行」：

| 问题 | 回复要点 |
| --- | --- |
| 权限多了 | 声明了 X 但代码里没用到；请去掉或说明用途 |
| 权限少了 | 代码调了 `ctx.notifications`，清单里没有 `notification` —— 现在会在运行到那一步才失败 |
| `.lcp` 与源码不一致 | 包里的 `index.js` 与源码不一致，请重新打包并重新提交 `dist/` |
| 缺 LICENSE / README | 详情页的正文来自 tag 下的 `README.md`，缺了会显示空白页 |
| 版本号没递增 | 索引里的 `latest` 已是 X，请升到 X 以上（新增权限属于 MAJOR） |
| ID 被占用 | 该 ID 已属于已发布的插件，请换一个 |

**不要替作者改代码后合并。** 插件是作者的版权作品（见[版权与授权](https://github.com/Rinntheor/modulith-desktop/blob/main/docs/07-法务/版权与授权.md)），改动应当由他确认；维护者负责的是审与签。

## 6. 一页速查

```
PR 进来
  → 先判断该不该收（CONTRIBUTING.md 第 1 节：投稿尚未开放）
  → 切到分支，逐条审核
      结构 / ID 占用 / 版本递增 / 权限必要性 / 通读代码 / 包与源码逐字节一致 / --check
  → 通过则 --no-ff 合并进 main
  → node scripts/build.ts            ← 合并后重新生成，绝不用 PR 里的
  → git diff index.json              ← 只应看到这一个插件的几行
  → pnpm tauri signer sign -f <key> index.json
  → git add index.json index.json.sig（同一个提交）
  → git push origin main
  → git tag -a <目录名>-v<版本> 并推送  ← 索引里的 tag 字段就是它
  → purge jsDelivr（想立刻生效）
  → 干净环境装一遍，重开后状态还在
```

**最容易出事的三个点**：① 在 PR 分支上签名而不是合并后的索引；② 忘了打 tag（用户点安装 404）；③ 没重新生成索引（哈希与包对不上，安装时被校验拒绝）。

**审核的核心不是「代码写得好不好」，而是「这份权限列表是否如实描述了它要做的事」** —— 因为那是用户唯一能看到的东西。
