# 划词翻译

一个**跑在本机的翻译工具**：贴一段文字、选两个语言、拿到译文，翻过的东西会留在历史里，可以搜索、置顶、随时复制回去。译文由**你自己跑在本机的**模型服务生成（llama.cpp 的 `server`、或者任何 OpenAI 兼容的本地端点），原文与译文都不离开这台机器，也没有任何一行进日志。

在此之上还有一条**可选的**入口：在别的程序里选中文字，按一下 `Ctrl+Q`，光标旁边弹出译文卡片 —— 不用切窗口就能用同一个工具。它需要 Node 运行时（后台是一个没有窗口的 Node 进程）与 Windows，而翻译工作台两样都不需要。

这个插件因此由两半组成，它们跑在两个**互不相通**的地方：那个 Node 进程（`background.js`，负责热键与划词翻译），以及你在侧边栏里看到的这个面板（`index.js`，负责翻译工作台、历史、语言与其它配置）。README 里凡是两者行为不同的地方都会写明是哪一半。

## 功能

| 功能 | 怎么用 |
| --- | --- |
| 翻译 | 面板最上面：输入原文 → 选源/目标语言 → 「翻译」（或者 `Ctrl + Enter`） |
| 复制译文 | 译文下面的「复制译文」；历史里每一条也有「复制」 |
| 翻译历史 | 面板中段。持久保存、可搜索**译文全文**、可分页、可置顶（不被自动清理）、可单条删除、可清空 |
| 换语言 | 工作台里的两个选择器，选过就记住；宿主设置页里也有同名两项 |
| 划词翻译 | 在任意程序里选中文字 → 按 `Ctrl+Q`（可改） → 光标旁的卡片上是译文 |
| 发现模型 | 「模型与端点」那一节的「同步模型」，见下面 |
| 改提示词 | 同一节里的模板编辑框。本地小模型对提示词格式极其敏感，因此这一项必须能改 |
| 看状态 | 「划词热键流程」那一节：热键注册上了没有、端点通不通、后台有没有上报 |
| 看统计 | 「统计」那一节：条目数、置顶数、译文总量、数据库文件大小 |

## 第一次用（三步）

1. **把模型服务跑起来。** 以 llama.cpp 为例：

   ```bash
   llama-server -m "Hy MT2 1.8B Q4_K_M.gguf" --port 5566
   ```

   它默认就在 `http://127.0.0.1:5566/v1` 上提供一个 OpenAI 兼容接口，这也正是本插件
   `baseUrl` 的缺省值。模型叫什么名字取决于你加载的那个文件 —— 不要手打，用下一步。

2. **在面板里点「同步模型」。** 插件会 `GET {base}/models`，把服务端**实际加载**的
   模型读回来。只有一个模型时（本地单模型是常态）它会被**自动选中**；有多个时列出
   来让你点一个。

3. **在工作台里翻一段。** 不想用热键就这样即可 —— 这个工具的全部能力都在面板里。
   要用划词热键的话，按一次 `Ctrl+Q`；如果服务端要求密钥而你没填，卡片上会显示
   服务端的原话与一句「检查 API key」。密钥在「划词热键流程」那一节里输入，写进的
   是**加密密钥库**而不是设置。

## 翻译工作台

面板上下来的第一块内容就是它：原文输入框、源语言、目标语言、「翻译」。

- 输入上限是 8000 字符。这不是配额，而是"本地小模型翻一整本书"没有意义 ——
  撞上它比让请求在服务端超时更容易理解。
- `Ctrl + Enter` 直接翻（多行输入框里它与"换行"不冲突）。
- 语言选择**会被记住**（写进设置），下次打开还是那两项。
- 「清空」只清这一屏的输入与结果，**不动历史**。

### 源语言里的「自动」是一句说明，不是一个语言名

本插件**不做语言检测** —— 那需要另一个模型，而本机通常只加载了一个翻译模型。
因此「自动」时模板里的 `{source}` 被替换成**一句让模型自己判断的话**，而不是随便
猜一个语言名（或者干脆留空）。猜错的后果是模型收到一条自相矛盾的指令，而译文里
的表现是"多了一句解释"，用户完全看不出那是提示词的问题。

选一个具体语言时 `{source}` 就是那个语言名。

## 翻译历史

**持久保存在 `ctx.db`**（一个插件一个 SQLite，宿主侧执行）。这是这一版最重要的
变化：划词翻译工具的本体是"翻过的东西还能找回来"，而"翻完就没了"是一个不可用的
工具。

| 操作 | 说明 |
| --- | --- |
| 搜索 | 在**译文全文**上搜，不是只搜列表里那 200 个字符的预览 |
| 打开 | 把这一条的**全文**取回来放进结果区（列表里只有预览） |
| 复制 | 取全文并写进剪贴板 |
| 置顶 | 置顶的条目不计入条数上限、也不被超龄删除 |
| 删除 | 删掉这一条（两张表一起删，不留正文残骸） |
| 清空未置顶 / 全部清空 | 两个按钮分得很清楚 —— "清空"到底清多少是用户该知道的事 |
| 加载更多 | 游标分页，一次 30 条 |

### 保留策略

1. **超龄**：`at` 早于 **180 天**的**未置顶**条目，连正文一起删；
2. **超量**：未置顶条目从最旧的开始删，直到不超过 **800 条**；
3. **体积硬顶**：存下来的译文总字符数超过 **约 400 万字符**时，从最旧的开始删,
   **这一步会删到置顶条目**（总量与库本身的大小是一件事），删到时记一条警告；
4. 每一轮裁剪都有扫描上限，且**裁剪失败绝不会影响"记下这条"** —— 那一刻译文
   已经在屏幕上了。

**原文不进历史**，只有它的字符数。存原文意味着把你粘进来的每一段话都落一次盘，
而一段被翻译的文字里出现密码、密钥、合同条款的概率一点也不低。代价是"打开历史
之后不能再翻一次"（要再翻就重新粘一次），这一版明确接受这个代价。

### 表结构

```sql
translate_entries (
  id            INTEGER PRIMARY KEY,   -- 自增，同时是游标分页的第二排序键
  at            INTEGER NOT NULL,      -- 翻译完成的毫秒时间戳
  source_lang   TEXT NOT NULL,         -- 这次用的源语言设置（'auto' 或语言名）
  target_lang   TEXT NOT NULL,
  model         TEXT NOT NULL,         -- 这次请求体里的 model
  src_chars     INTEGER NOT NULL,      -- 原文的字符数（只用于统计）
  body_preview  TEXT NOT NULL,         -- 译文的前 200 个字符
  body_chars    INTEGER NOT NULL,      -- 存下来的译文字符数
  pinned        INTEGER NOT NULL
);
translate_bodies (id INTEGER PRIMARY KEY, body TEXT NOT NULL);  -- 全文

CREATE INDEX translate_entries_recency ON translate_entries (at DESC, id DESC);
CREATE INDEX translate_entries_pinned  ON translate_entries (pinned) WHERE pinned = 1;
```

**预览与全文为什么分开**：列表一次要取 30 行，而一段译文可能上千字符 —— 只为渲染
每行两行高的预览就把几百 KB 搬进 JS 是没必要的。全文只在"打开这一条 / 复制这一条"
时按 id 取一行。这条设计抄自 `plugins/clipboard-history/`（它已经在真实使用里把长
文本历史的坑踩过一遍），游标分页、按真实查询建索引、每轮裁剪带扫描上限也都是从那
一份搬过来的。

## 它往哪里发请求，发的到底是什么

两个都必须是 **OpenAI 兼容层**（base URL 以 `/v1` 结尾时的那两个路径），而不是
llama.cpp 的**单数**原生接口 `/completion` —— 后者收的字段名不同。

**`endpointKind = chat`（缺省）** —— `POST {base}/chat/completions`：

```json
{
  "model": "Hy MT2 1.8B Q4_K_M.gguf",
  "messages": [{ "role": "user", "content": "<按模板拼好的整段提示词>" }],
  "temperature": 0,
  "max_tokens": 1024,
  "stream": false
}
```

**`endpointKind = completion`** —— `POST {base}/completions`：

```json
{
  "model": "Hy MT2 1.8B Q4_K_M.gguf",
  "prompt": "<按模板拼好的整段提示词>",
  "temperature": 0,
  "max_tokens": 1024,
  "stream": false
}
```

两者的 `model` 都在**请求体**里，不在路径里 —— OpenAI 兼容接口上没有
`/models/<名字>/...` 这种形式，把模型名拼进 URL 的后果是换模型时得到一个 404，
而 404 不会告诉你是这件事。

还有一条只读的请求：**`GET {base}/models`**，用于「同步模型」。它不带任何用户内容。

**为什么要留 `completion` 这一档。** 有些 llama.cpp 构建在 `/v1/chat/completions`
上表现不稳（模板被套两层、或者干脆忽略指令），而在 `/v1/completions` 上把提示词当
一段纯文本续写反而干净。两者都留下，让使用者按自己的构建选 —— 而不是由作者替所有
构建赌一个。

### 响应是怎么解析的

- `chat`：先取 `choices[0].message.content`；
- `completion`：先取 `choices[0].text`；
- 取不到就试另一个（有些构建在 `/completions` 上回的是 message 形状，那是它的实现
  细节，不该变成使用者面前的一句"没有译文"）；
- **两个都没有时不返回空串**，而是报出 `choices[0]` 的**字段结构**（不是内容 ——
  响应体里可能回显提示词，而提示词里就是原文）。空串会被上层当成一次成功的翻译，
  然后用户看到一张空卡片。

### 提示词模板可以改，而且这是必须的

缺省模板是：

```
把下面这段文本翻译成{target}。只输出译文本身，不要解释、不要加引号、不要重复原文。

{text}
```

三个占位符：`{text}`（**必需**，没有它的模板会被换成缺省模板）、`{target}`、
`{source}`。

**为什么它必须可改。** 本地小翻译模型对提示词格式的敏感程度超出一般印象：同一个
模型换一种问法就从不翻译变成开始解释，而不同的模型（翻译专用的、通用的、不同量化
版本的）认的格式又不一样。写死一个模板的后果是**这个插件只在作者那一个模型上能用**，
使用者拿到的是一句"模型不听话"，而他能做的事只有放弃。

用通用小模型（指令跟随较弱）时，把指令换成英文往往更稳：

```
Translate the following text into {target}.
Output only the translation, without quotes or explanations.

{text}
```

`{text}` **最后**被替换，因此你输入的原文里如果恰好有 `{target}` 这样的字面量，它不会
被再替换一次（一段讲模板语法的技术文档正好会这样）。

## 模型同步：「同步模型」到底在分辨什么

`GET {base}/models` 会以三种截然不同的方式失败，而它们各自要你做的事完全不同。
插件把它们分开报，而不是笼统说一句「同步失败」：

| 看到的话 | 真正发生了什么 | 你该做什么 |
| --- | --- | --- |
| 连不上（服务没在跑） | TCP 连接被拒绝 —— 那个端口上没有东西在听 | 把 `llama-server` 跑起来 |
| 不是 OpenAI 兼容接口 | HTTP 404 / 405 —— 服务在，但这个路径上没有兼容层 | 改 base URL（多半是漏了结尾的 `/v1`，或者填成了单数的 `/completion`） |
| 服务在跑，但一个模型都没加载 | 200 且 `data` 是空的 | 在服务端用 `-m` 指一个 gguf 文件 |
| 服务端要求密钥（401） | HTTP 401 / 403 | 检查那一节里的 API key |

结果会**缓存**（连同探测时刻），因此打开面板不会去戳一次端点。状态行里显示的是
"上次探测"的结果与它发生在多久以前 —— 那不是"现在通不通"，而是"最后一次确认通的
时候是什么时候"。要更新就再点一次「同步模型」。

## API key

**它不进设置，也不进插件的任何文件。** 输入之后写进 `ctx.secrets`：密文落在
**插件数据目录之外**（`<app_data_dir>/plugin_secrets/<插件 id>.json`），密钥由本机
硬件指纹派生，而且**不属于任何备份类别**。

代价明明白白写在面板上、也必须被说出来：**换机器（或换网卡、改主机名）之后解不开。**
那时后台的 `ctx.secrets.get` 会**抛错**（不是返回 `null` —— 返回 `null` 会被读成
"用户还没配置密钥"，然后引导他重新输入一遍，而密文其实还好端端地躺在磁盘上）。
卡片上显示的是宿主那句原话，里面写着"密文仍然在磁盘上、没有被删除"。重新输入一次即可。

面板上的输入框：

- 是 `type="password"`，而且**`value` 永远是空的** —— 已保存的密钥**不会**被渲染进
  DOM。把它作为 `value` 写进去等于把它放进一个可以被截图、被开发者工具读出来的地方。
- 旁边只显示"已保存 / 未设置"，那份状态来自 `ctx.secrets.keys()` —— 它**只有键名，
  没有任何值**。
- 留空点「保存密钥」= **删除**（也等于"我不想再用密钥了"，同时避免写进去一个空串，
  那会让服务端收到一个畸形的 `Authorization: Bearer ` 头）。

本地 llama.cpp 的 server 默认**不校验**密钥，因此留空也能用。插件在密钥缺失时不发
`Authorization` 头，而不是发一个空的。

## 隐私：这个插件能看到什么，以及它把什么留在哪里

它拿得到两样别人看不到的东西：**你输入的（或选中的）文字**，以及**那段文字的译文**。
因此：

**原文与译文一个字都不进** `console`、`ctx.logger`、`ctx.notifications`。理由是三件
具体的事：

- `modulith.log` 是明文文件，而且用户会把它发给维护者排查问题 —— 而他选中的可能是
  正在编辑的合同，也可能是复制失败之后留在剪贴板上的密码；
- 通知会留在通知中心里，重启之后还在；
- 那是三条"用户看不见、又不会自己消失"的通道。

它们只出现在四个地方，而且每一个都是用户自己要的：

| 去处 | 理由 |
| --- | --- |
| 面板的 DOM | 就是他面前这一屏 |
| 剪贴板 | 他自己按的「复制」按钮 |
| 光标旁的卡片 | 热键翻出来的结果，贴的是他自己屏幕上的光标，不落盘 |
| **`ctx.db` 的历史表** | 划词翻译工具必须能把刚才翻过的东西找回来（只有译文，没有原文） |

第三处与第四处是**互不相同**的两个出口，这一点值得说清楚：热键翻出来的译文**只**进
卡片，**不会**进历史。后台那半跑在另一个进程里，它拿到的是一段用户选中、可能含密码
的文字，而把"要不要留档"的决定交给一次按键太轻率了。代价见下面「已知的取舍」。

第四处的代价也必须写明：历史落在插件的**数据目录**里（`<data>/plugin.db`），而
「插件数据」是备份的一个类别 —— 因此它会随备份复制到别的机器上。面板上有逐条删除、
「清空未置顶」与「全部清空」；历史**不提供导出**，也不写任何一份明文副本到别处；
**原文根本不进库**（只有它的字符数）。

运行状态（热键那一节读的那份）里只有代码、时间与地址：`hotkeyState`、`hotkeyError`
（宿主那句话，它点名的是**谁占着组合键**，不是任何用户内容）、`endpoint`、`model`
这些。没有原文，没有译文。

**唯一的例外，而且它是有意的：** 模型服务返回的 **HTTP 响应体**在非 2xx 时会被截断
（600 字符）后显示出来 —— 因为"翻译失败"这四个字对使用者毫无用处，而服务端那句话
往往就是解决办法。它**只**进那一屏（卡片或面板的提示条），不进日志、不进历史。
即便如此，那个响应体仍然按不可信输入处理：它可能回显提示词，而提示词里就是原文。

### ⚠️ 读选中文本会改你的剪贴板

这一项的内幕必须说清楚，因为它与用户的直觉不符：系统上"拿到别的程序里选中的文字"
只有两条路，插件走的是**合成一次 `Ctrl+C` 再读剪贴板**。因此：

| 内容 | 能否还原 |
| --- | --- |
| 文本 | ✅ 会被还原 |
| 图片、富文本、文件列表 | ❌ **无法还原**。`Ctrl+C` 的那一刻它们就没了 |

这是"要么接受，要么换 UI Automation"的取舍（而 UI Automation 在浏览器、Electron
应用与终端里大面积不生效，恰好是这类插件最常被用到的场景），不是实现缺陷。宿主在
捕获期间把剪贴板监测置为抑制态，因此这一次合成的复制**不会**往剪贴板历史里注入幻影
记录。

同一时刻只允许一次捕获；两次并发会拒绝第二次。捕获时限 400 ms，超时意味着那个程序
不响应这次 `Ctrl+C` —— 错误里会说明，而不是让你以为是权限问题。

## 已知的取舍与限制

### 热键翻出来的译文不会出现在历史里

两个进程之间只有宿主的存储与设置这一条**读—写**通道，没有推送；而历史由面板这一半
写。让后台也去写同一张表意味着把一个没有界面的进程当成"用户已经同意留档" —— 而它
拿到的可能是一段密码。因此两条路是**分开**的：热键的结果只在卡片上，想留档就在面板
里再翻一次（或者用面板里的工作台）。这一条在面板上也写着。

### 原文不进历史

见「翻译历史」那一节。要"打开之后再翻一次"就得把原文落盘，而这一版明确不付那个代价。

### 历史里的搜索是 `LIKE`，不是全文索引

`LIKE '%词%'` 在几万条上仍然够快，但它**不认同义词、不做分词**。数据量再上一个数量级
时该换成 FTS5（宿主已经开着 SQLite，那是加一张虚拟表的事）—— 现在不做，因为那会让
库变大、并多一套需要维护的写入路径。

### 面板不会自动更新

没有推送通道。面板在**打开 / 重新可见 / 你点「刷新」**时读一次后台写下的状态与第一
页历史。刻意不挂定时轮询：那会让这个插件在后台一直发 RPC，换来的只是更新一份你多半
没在看的缓存。

### 改组合键最多要等一分钟

`ctx.settings.onChange` 在**后台运行位置上不存在**（宿主没有一条"设置变了"的推送通道
给那个进程，见宿主文档 `现行问题` 条目）。因此后台对组合键的处理是**对账**：清单里
的 `contributes.background.interval` 是 60 秒，每一趟只做一件事 —— 把注册的组合键
换成设置里的那一条。

这个 `interval` **不是心跳**：翻译一次都不由它驱动（触发是宿主按热键推过来的），空
闲时那个进程什么都不做。它存在的唯一理由就是上面这件事，而它也不能更稀：组合键是
用户偶尔改一次的配置。其余配置（地址、模型、源语言、目标语言、提示词）没有这个滞后
—— 后台**每次触发都重读一遍**。

### 组合键在系统里是独占的

`RegisterHotKey` 一次成功的注册会把这个组合键从**这台机器上所有其它程序**手里拿走。
注册失败时错误里点名是谁占着：宿主快捷键、另一个插件、还是系统里的别的程序 —— 三种
情况下你能做的事完全不同，因此插件**一个字都不改写**那句话。

后台在换绑定时**先注册新的、成功了再解绑旧的**。反过来的话，注册失败之后你手里一条
绑定都不剩 —— 而失败的原因常常是"这个组合被别的程序占了"，那是换个键就能解决的事，
不该连原来那条也丢掉。

卸载、停用或退出应用时宿主会**自己**解绑（这是宿主那四条释放路径里的一条，也正是
"停用不一定经过插件的任何代码"那一类），因此插件不在自己的清理回调里再解一遍。

### 非 Windows 上没有热键流程

`RegisterHotKey` 与 `SendInput` 都只存在于 Windows。在别的平台上
`ctx.hotkey.isAvailable()` 与 `ctx.selection.isAvailable()` 都是 `false`，「划词热键
流程」那一节会显示一条明确的横幅说明这件事 —— 而上面的翻译工作台与历史照常可用，
这正是把它们做成主体的理由之一。

### 只声明了 `network`，因此远端端点用不了

`network` 放行的是**本机回环地址**（`127.0.0.1` / `localhost` / `::1`）。把 base URL
指向局域网或公网上的另一台机器时，宿主会拒绝这次请求，除非清单里同时声明
`network-external`。面板在地址看起来不是回环时会给出一句警告。

那是一条**新增权限**，按 `CONTRIBUTING.md` 第 5 节属于 MINOR 以上的版本变化（新增
中高风险权限会触发用户侧的确认流程），因此没有顺手加上。要用远端端点，改清单那一行
并升版本。

### 结果卡片会截断过长的译文

卡片正文的上限是 4000 字符（宿主强制）。译文超过它时，插件自己截断并补一句
「译文超过卡片的长度上限，已截断」—— **显示的上限就是复制的上限**，复制一份比看到的
更长的内容是那种"过一会儿才发现复制少了半句"的缺陷。`max_tokens` 是 1024，正常情况下
撞不到这个上限。

### 单条历史最多存 20000 字符

更长的译文被**截断后照常入库**，而不是拒绝这次翻译：用户已经拿到译文了，而"因为太长
所以没记"是一句他无法预料的解释。列表里的「原文 N 字符 · 译文 N 字符」显示的是**存
下来的**长度。

### `GET /models` 是唯一一次不经 POST 的请求

它不带任何用户内容，因此它的响应体可以安全地显示给用户（这也是"同步模型"能把服务端
原话摆出来的前提）。翻译那一路的响应体只进那一屏，理由见上面隐私那一节。

## 它用到的宿主能力

| 权限 | 用来做什么 |
| --- | --- |
| `storage` | 读设置项（`ctx.settings`）与后台写下的运行状态（`ctx.storage`）。这是两个进程之间唯一的通道 |
| `plugin-data` | `ctx.db`：翻译历史。一个插件一个 SQLite 文件，宿主侧执行、宿主侧限页数 |
| `network` | `ctx.http`：`POST /chat/completions` 或 `/completions`、`GET /models`。**只有 `network`，因此只放行本机回环地址** |
| `notification` | 结果卡片（`ctx.ui.popover`）需要它 —— 它与应用内通知是同一档：卡片出现时会打断用户正在做的事 |
| `clipboard` | 把译文放回剪贴板。**后台位置上只有 `writeText`**，而且走的是宿主（见下） |
| `secrets` | API key |
| `global-hotkey` | 注册触发组合键（只有 Windows） |
| `read-selection` | 读取前台程序里选中的文本（只有 Windows；⚠️ 会短暂覆盖剪贴板） |

**`plugin-data` 是本插件新增的一项，而它是必需的。** 没有它宿主不会给出 `ctx.db`，
翻译历史那一节会显示一句"这个运行位置没有 ctx.db"。权限必须与实际用法一致：多写一项
会让用户在插件详情里看到一条并不存在的能力，少写一项会让那个功能在运行时被拒绝。
`ctx.db` 的边界（`ATTACH` 被引擎级 authorizer 拒绝、页数上限、一次调用只编译一条语句）
全在宿主侧的 `modules/plugins/db.rs`，插件这一侧不需要（也做不到）自己加防线。

**为什么插件版本从 1.0.0 跳到 2.0.0。** 按 `CONTRIBUTING.md` 第 5 节，**新增权限属于
MAJOR**：权限变化会触发用户侧的确认流程（新增中高风险权限需要用户明确同意），把它当成
小版本会让升级在用户那里显得突然。这一版新增的正是 `plugin-data`。

**`clipboard` 在后台位置上是"半个成员"。** `ctx.clipboard` 在沙箱面板里有
`isAvailable / readText / writeText / canMonitor / subscribe / readFormats / readImage`，
而后台那个进程里**只有 `isAvailable` 与 `writeText`**：

- 观察那一半（`subscribe` / `canMonitor` / `readFormats` / `readImage`）需要一条
  「宿主 → 订阅者**界面**」的推送通道，而后台插件没有界面承载它；
- 读那一半在界面位置上是 `navigator.clipboard`，而那个进程里没有 `document`；
- 但**写入必须有**：结果卡片上的按钮只回一个 action id，真正把译文放进剪贴板的只能
  是插件这一侧。

沙箱那条写入调的是浏览器 API（前端强制），后台这条走宿主的 `clipboard.write`
（**Rust 侧判 `clipboard` 权限**，比前端强制更强一档）。方法名与形状两边逐字相同，
差别只在机制 —— 因此"同一个插件换个运行位置"在这里不需要改代码。

`storage`、`plugin-data` 与 `ctx.secrets` 的分工：设置、运行状态、模型列表缓存进
`storage`（明文，但里面**没有**任何用户内容）；翻译历史进 `ctx.db`（明文，含译文，
**不含原文**）；**只有 API key** 进 `secrets`。

## 目录结构

```
translate/
├── manifest.json      清单
├── index.js           手写 IIFE，无构建步骤：沙箱里的面板（工作台 + 历史 + 配置）
├── background.js      手写 IIFE：无窗口的 Node 进程，热键与划词翻译
├── index.css          插件自带样式（类名统一 tr- 前缀，复用宿主的 --accent-*）
├── icon.svg           图标
├── README.md          就是这一份，会显示在插件详情抽屉里
└── LICENSE            MIT
```

`index.js` 与 `background.js` 是**两个独立的文件，不是模块**：单文件 IIFE 的插件不
允许 `import`（宿主只给一个可执行的 JS 文件，`background.js` 连 `require` 都没有）。
因此两边各有一份完全相同的小工具（HTTP 归一化、提示词拼装、响应解析、缺省值）——
这是**刻意抄的两份**，改动必须两处一起改。清单里那七个设置项的缺省值也必须是同一批
值，也就是三处。

**历史只在 `index.js` 那一侧。** 后台进程连 SQL 都不发 —— 它拿到的是一段用户选中、
可能含密码的文字，让它顺手写库是一个不该由一个按键触发的决定。

## 版本前提

清单里写的是 `"engines": { "modulith": ">=1.6.4" }`，插件版本是 **2.0.0**。

**这个下限不能再低。** 本插件依赖四样 1.6.x 才有的东西：

1. `ctx.hotkey` 与 `ctx.selection`（宿主侧 `hotkey.rs` / `selection.rs`，含
   `global-hotkey` 与 `read-selection` 两项权限）；
2. **后台运行位置上的 `ctx.secrets` 与 `ctx.clipboard.writeText`**（`background-host.mjs`
   与 `rpc.rs` 的 `clipboard.write`）；
3. `ctx.db` 与它背后的 `plugin-data` 权限（1.6.0 起有）—— 翻译历史整个建立在这上面；
4. `ctx.ui.popover`（结果卡片）。

更旧的宿主不会给出任何兼容性提示，而插件在里面根本跑不起来：后台那一半会拿不到
密钥、也放不进剪贴板；没有 `ctx.db` 时历史那一节会明确报"这个运行位置没有 ctx.db"，
而不会静默地什么都不记。

因此**宿主必须先发布带这几样的版本，本插件才能上架**；在此之前它只能以开发链接的
方式在本机试用。若最终发布时宿主改了版本号，这里的字符串必须跟着改**并重新打包**
—— 包变了就升插件版本，不要在原版本号上覆盖产物。
